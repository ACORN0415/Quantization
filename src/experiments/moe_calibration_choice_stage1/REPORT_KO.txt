적은 보정 자료에서 MoE 전문가의 GPTQ/RTN 선택: 제한 진단 결과
2026-11-01, 한국 시간

이번 조건에서는 공통 설정 선택으로 충분했다. 전문가별 선택기 개발을 종료한다.

선택용 네 문서만 사용했을 때 전문가 43·62·51·17은 모두 GPTQ damping 1.0을
선택했다. 네 전문가를 합쳐 공통 설정 하나를 고르는 방법도 같은 설정을 골랐다.
보류 16문서에서 전문가별 선택의 공통 선택 대비 오차 감소는 정확히 0%다.
이는 같은 후보 출력을 사용하는 두 정책의 비교다. 모집단에서 서로 다른 정책이
동등하다는 통계적 증거나, 모든 MoE에 전문가별 선택이 불필요하다는 결론은 아니다.

반면 선택한 공통 설정은 고정 RTN보다 투영 오차를 9.2024%, 고정 GPTQ 0.01보다
32.7875% 줄였다. 관측한 의미는 '설정 선택은 도움이 됐지만 전문가마다 다르게
선택할 필요는 없었다'이다. 새 선택기가 필요한 미해결 문제는 확인하지 못했다.

통제와 실행 전 수정 기록

  공개 Olive revision 1647eb2b589ae8a82b2dbe4429e5fe4335c40092의
  gptq_quantize_weight 함수와 WeightQuantizer를 원문 그대로 보존·사용했다.
  전체 Olive/GPTQModel 패키지의 실행이나 두 패키지 간 성능 비교가 아니다.
  전문가마다 원본 W·H를 보존하고, 모든 후보에 별도 복사본을 전달했다.
  원본 원소 바이트 해시를 후보마다 확인한 20건 모두 변경이 없었다.

  INT4, group128, 대칭 absmax scale, unsigned 코드 0~15, zero point 8,
  FP32 scale·INT32 zero point, ties-to-even 반올림, 코드 범위 clipping,
  actorder=False, blocksize128을 고정했다. Hessian은 보정 입력만으로
  H=2*X.T@X/N을 FP32로 계산했다. TF32는 껐다.
  모든 후보의 코드·scale·zero point payload는 1,179,648바이트로 같았다.
  네 전문가 합계는 4,718,592바이트(4.5 MiB)다. 파일 컨테이너 크기는 별도 기록했다.

  후보 생성 전에 두 실행이 중단됐다. 모두 실제 가중치 후보는 0개였다.
  1) 결정적 cuBLAS 실행에 필요한 환경 변수가 없어 첫 무개입 연산이 거부됐다.
     CUBLAS_WORKSPACE_CONFIG=:4096:8을 설정했고 실패 로그를 보존했다.
  2) 원래 fused gate/up 연산에서 up만 별도 GEMM으로 떼면 BF16 비트 일치가
     깨졌다. 새 경로도 원래 fused 행렬 형상과 행 순서를 유지하도록 수정했다.
     양자화한 up 행만 교체하고, 결과의 up 부분만 평가한다.
  허용오차를 완화하지 않았다. 수정은 후보 생성·오차 관측 전에 기록·커밋했다.
  최초 등록 b2597ed → 환경 기록 9da5a83 → 원래 연산 보존 27d476f 순서다.
  이전 등록본과 실패 기록은 Git과 attempt01/attempt02 디렉토리에 남아 있다.
  최종 원문·실행 코드 해시는 registration.json에 기록했다.

  이후 무개입 24문서×4전문가=96건의 BF16 원소 바이트 일치와 실제 후보 20개의
  패킹 왕복·FP32 복원 일치를 통과했다. 작은 독립 NumPy GPTQ 검사는 정상·
  낮은 rank·입력이 0인 열을 포함하며, 후보 순서 반전에서도 출력이 같았다.

  GPTQ 고정에는 보정 입력 접근과 Hessian 수집, 해당 설정 하나만 포함했다.
  공통·전문가별 선택은 동일한 후보 생성·선택용 평가 결과를 공유한다. 두 행의

  최솟값을 고르는 계산은 공통0.0000564초·전문가별0.0000168초다. 작은 차이를
  계산 가속으로 해석하지 않는다. 상세 구성요소는 audit.json의 costs에 있다.
  무개입 검사·해시·native 추가 검사·보류 평가·기록 파일 저장은 진단 비용이다.

  유효 GPU 단계 경과시간은6.6204초다. 20개 생성과 선택 단계5.8453초,
  보류 평가0.3423초이며 나머지 초기화·무개입 검사·기록 작업도 전체에 포함된다.
  후보 이전의 두 실패 실행은 합쳐10초 미만이었고 전체60분 상한에 포함했다.
  마지막 유효 실행의 경과 상한을590초로 두어 GPU 단계 총600초 상한도 지켰다.

  reserved는192,937,984바이트, CPU RSS는1,918,251,008바이트다.
  한 전문가의 W·선택 입력과, GPTQ 시작 후에는 H를 GPU에 두었다. native 검사를
  위한 원래 fused 가중치도 보유했다. 전체 모델을 GPU에 올리지 않았다.
  이 최대치는 정책별 독립 최대 메모리가 아니며 RTN/GPTQ의 메모리 우열로 쓰지 않는다.
  새 원자료는 약148 MiB로512 MiB 상한 안이다. 시간·파일 보존 완료 시각은
  completion.json에 기록한다. 별도 배포 지연·보정 예산 요구는 주어지지 않았다.
  직접 선택이 '비싸서 부족하다'는 결론을 내릴 근거는 없다.

보존 자료의 재검증

  verify_moe_calibration_choice.py는 GPU를 사용하지 않는 읽기 전용 검사다.
  현재 시각이 과거 실행 마감 전일 필요가 없고, 저장 기록을 덮어쓰지 않는다.
  원자료26개 파일의 크기·해시, 입력2개 파일과 고정 코드 해시를 확인했다.
  공개 양자화 도구와 별도로 nibble을 풀고 FP32로 복원한20개 후보가 저장된
  전체 원소 바이트 해시와 같았다. 원래 W와 저장된 H의 해시도 확인했다.
  선택80건·보류320건의 FP64 제곱오차400개를 CPU 행렬곱으로 다시 계산했다.
  GPU 기록 대비 최대 절대 차이는5.68434e-14, 최대 상대 차이는3.92597e-16이었다.
  저장된 native GPU 출력과 기준 출력으로 재계산한 제곱오차의 최대 차이는
  1.13687e-13이었다. native GPU 연산 자체를 CPU로 재현했다는 뜻은 아니다.
  선택용 점수만으로 선택을 재계산해 기존 기록과 일치함을 확인했다.

판단과 종료 범위

  이번 질문인 '전문가별로 다르게 선택할 실익이 있는가?'에는 아니라고 답한다.
  적은 자료에서도 작은 분할 검증으로 공통 설정을 고르면 이번 후보 집합에서는
  전문가별 선택과 같았다. 고정 RTN이나 기본 damping 하나만으로 검사를 끝냈다면
  놓쳤을 개선은 있었지만, 기존 직접 평가 기준선이 그 개선을 확보했다.
  GPTQ 1.0을 다른 모델·입력에 검증 없이 고정하라고 권고하지 않는다.

  새 선택기·추가 damping·추가 전문가·전체 모델 평가로 확대하지 않는다.
  보정 불균형과 분할 검증에 의한 설정 선택은 기존 연구가 다루는 문제이므로
  이 결과를 새 방법이나 새로운 실패 원인의 발견으로 제시하지 않는다.
  종료 범위는 이 한 층·네 전문가·up 투영·후보 집합·보정 규모의 선택기 개발이다.
  MoE 연구 전체를 종료하거나 보정 표본 수의 일반 임계값을 제안하는 것이 아니다.
