# post-W_O 전환 rounding 개발 진단 — 고정 설정 NO-GO

2026-10-29 23:20 KST 완료. [실행 전 계획](../POSTWO_ROUNDING_DEVELOPMENT.md)을 `abd5ef2`로 커밋한 뒤 측정했다. **현재 청크 query에서 선택한 전환 rounding이 다음 청크 query의 전환 오차를 줄이지 못했다.** 고정한 10% 개선 조건에 못 미쳐 이번 설정은 NO-GO다. 영상 품질 실패나 전환 기반 양자화 전체의 불가능성을 뜻하지 않는다.

## 이전 대수 검사에서 무엇이 달라졌는가

pre-W_O head별 오차에서는 같은 query의 삭제 전후 손실이 scalar 가중 출력 오차로 환원됐다. 이번에는 실제 출력 투영 W_O가 head를 섞는 전체 오차를 사용했다. 이 경우 교차항이 생겨 독립적인 scalar head 가중치만으로 일반 표현되지 않는다. [합성·대수 검사](../POSTWO_TRANSITION_GATE_KO.md)는 그 차이를 확인했다. 일반 이차 metric으로 쓸 수 있다는 사실만으로 신규성이나 실용성을 판정하지 않았다.

확인한 [OptR](https://arxiv.org/html/2608.02691v1) §4.4–4.5의 식은 **head별 투영 오차 norm을 더하는** 형태다. 전체 head 오차를 먼저 합한 norm과 다르다. 이 판단은 논문의 명시적 목적 기준이며 공식 구현까지 대조한 것은 아니다. [AATC](https://arxiv.org/html/2608.14191v1)의 독립·영평균 오차 가정하 왜곡 분해도 이번 실제 코드 교차항 최적화와 동일하지 않다. 제한된 문헌 검토이며 완전한 신규성 보증은 아니다. head별 보조 팔은 OptR 전체 방법 재현이 아니다.

## 입력·비교

개발 p0/p4·seed101, 층 0/14/29에서 BF16 첫 8청크를 다시 실행했다. 청크6 최종 refresh의 전체 post-RoPE K(0..6), 새 V(청크6)와 W_O를 캡처했다. 선택 Q는 청크6 refresh, 평가 Q는 청크7 첫 denoise에서 각각 고정 linspace 32개를 얻었다. 평가 Q는 코드 선택에 쓰지 않았다. 두 Q 모두 BF16 teacher 실행에서 나온 것이며 압축 rollout은 아니다.

같은 Q를 청크0..6 K에 적용한 상태와, 청크0만 삭제한 상태를 비교했다. 청크7 K/V는 추가하지 않았다. **실제 전환 전체가 아닌 반사실적 attention 진단**이다. K16 고정, 새 V4/g16만 고정 FP16 scale의 floor/ceil 중 선택했다. 과거 V 오차를 계산에 넣지 않고 새 V 양자화가 추가한 출력 오차만 측정했으므로, 과거 BF16 V 원본을 무비용 buffer로 사용하지 않았다. 실제 압축 캐시의 전체 오차가 0이라는 뜻은 아니다.

FP32 QK softmax·AV·W_O를 사용했다. BF16 FlashAttention 출력의 비트 재현이라고 주장하지 않는다. 다음 네 팔에 동일 RTN 초기 후보·32회 projected-gradient 예산(최적화 팔)을 적용했다.

- RTN.
- 전체 post-W_O 평균 오차 D 최소화, λ0.
- 전체 post-W_O D+J 최소화, λ1.
- head별 post-W_O 기여 norm을 더한 D+J, λ1.

D는 삭제 전후 출력 오차 제곱의 평균, J는 두 오차 차이의 제곱이다. 모든 결과는 query 32개×출력 1536차원으로 나눴다. 주 대비는 **전체 λ1 대 전체 λ0**이며, 3층을 동일 가중했다. 입력 2개×3층×4팔=24행이다. 새 보류 연구가 아니며 p값을 계산하지 않았다.

## 최적화·해석의 중요한 한계

코드가 전혀 움직이지 않은 결과는 아니다. 최적화 18셀 모두 11–201개 scalar 코드가 바뀌었고, 각 목적은 해당 RTN 초기의 94.72–99.51%로 줄었다. 실제 새 V scalar는 층마다 7,188,480개여서 코드 변경 비율은 약 0.00015–0.00280%로 작다. 이것은 탐색이 활성화됐다는 확인이며 충분히 수렴했다는 증거는 아니다.

사후 읽기 전용 확인에서 **전체 λ0의 후보가 전체 λ1의 후보보다 선택 Q의 D+J에서도 6셀 모두 낮거나 같았다**(4셀 낮음, 2셀 동률). 즉 이번 λ1 탐색은 같은 예산에서 다른 팔이 찾은 후보도 넘어서는 최적화를 하지 못했다. 따라서 이번 실패를 전환 목적 자체의 실패로 해석하면 안 된다. 후보를 사후 교환하거나 탐색을 늘려 고정 주 결과를 수정하지 않았다.

또한 RTN에서 선택 Q의 J/D는 0.000138–0.007443인 반면 평가 Q에서는 0.01197–0.24126이었다. 고정 λ1에서는 선택 단계 전환 항의 비중이 작았고 query 분포도 달랐다. 결과를 본 뒤 λ를 조정하지 않았다. 현재 판정은 **이 query·가중치·탐색 규칙·32회 예산에서 이득을 보여주지 못했다**는 범위다.

RTN 평가에서 전체/head별 D의 비는 p0 0.99190/p4 0.99254, J의 비는 1.00217/0.99787이었다. 교차항은 존재하지만 이번 표본의 합산 오차에서 큰 차이를 만들지는 않았다. 합성 반례의 큰 상쇄 효과가 실제 모델에서도 크다는 증거는 얻지 못했다. 층별 효과와 train/eval 전체·head별 metric은 [CSV](rows.csv)에 보존했다.

## 저장량·시간·자원

모든 팔의 **새 V 한 청크/한 층** payload는 실제 uint8 컨테이너 8,100,864바이트, 가상 packed 추정 4,500,480바이트로 같다. scale·padding을 포함한다. K는 BF16 그대로이며 전체 KV를 INT4로 압축한 실험이 아니다. 원본/복원 tensor와 W_O·Q/K 진단 작업공간은 이 payload 밖이다. 가상 packed를 실제 GPU 메모리로 부르지 않는다.

실측 탐색은 32회 한 번 실행한 값으로, 6개 입력×층 셀의 중앙값은 전체 λ0 84.23ms, 전체 λ1 84.18ms, head별 λ1 92.03ms였다. RTN 행의 시간은 이미 준비한 초기 객체를 선택하는 시간이라 RTN encode latency로 읽으면 안 된다. Wo spectral norm 계산(층/입력당 약 93–147ms), query 확률 준비(첫 호출 74ms, 이후 약 2.3ms), 파일 IO는 팔별 탐색 시간 밖이며 별도 기록했다. 준비 비용을 포함한 배포 추론 지연이나 최적화 kernel 성능으로 해석하지 않는다.

캡처는 모델·텍스트 로딩과 계측 포함 프롬프트당 58.6/58.8초였다. 캡처 peak allocated 8.638GiB, reserved 9.039GiB, CPU high-water 약 33.18GiB였다. 별도 분석·탐색 루프 3.84초, 그 프로세스 peak allocated 0.648GiB/reserved 0.771GiB다. 모델 및 진단 실행의 자원이며 배포 cache 절감 근거가 아니다. 캡처 12개 0.670GiB와 코드 24개 0.181GiB를 로컬에 보관했다. 추가 영상은 만들지 않았다.

## 검증과 종료 범위

CPU core 검사 7개, 대수 목적/gradient 128건·이웃 rounding 16후보·특수 경우 2개·전체 과거 offset 4건이 통과했다. 관찰 hook을 단 BF16 prefix도 16/16청크에서 비트 일치했다. 소스는 캡처/분석 전후 같았고, 읽기 전용 감사는 결과 24행·캡처 12개·코드 24개·탐색 24개의 해시와 실제 query 시점·형상·고정 scale·범위·padding·동일 payload·판단을 확인했다. 같은 작성 주체의 재검토이며 외부 독립 검증은 아니다. 감사가 모델/attention 계산을 별도로 다시 실행한 것도 아니다.

```bash
cd ~/Quantization
~/sfq_data/py tools/audit_postwo_round_probe.py --tensors
bash tools/watch_progress.sh 0
```

고정한 이번 변형은 종료한다. 새 query·λ·탐색 예산·K 양자화를 바꿔 결과를 구제하지 않는다. 기존 자료의 영상 품질 결론은 바꾸지 않았고, post-W_O 전환 rounding의 배포 가능한 신규 방법도 확보하지 못했다. 추가 투자를 검토한다면 미사용 query 전이와 최적화 효율을 해결하는 구체적인 알고리즘이 먼저 필요하다.
