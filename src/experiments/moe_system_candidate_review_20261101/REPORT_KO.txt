MoE 실행 후보 두 개 검토와 다음 자원 배분
2026-11-01 / CPU·문헌·공개 코드 확인 / GPU 실험 없음

판단
다음 자원은 “추측 검증에서 거절된 토큰의 전문가 접근이 이후 GPU 캐시
재사용과 전송량에 어떤 영향을 주는가”라는 작은 진단에 배정한다.
새 연구 방법으로 채택한 것은 아직 없다. 전문가/KV 메모리 공동 배분이라는
다른 후보는 현재의 넓은 정의로는 제외한다. 완료한 보정·배분 후보는 재개하지 않는다.

현재 확보한 것은 GPU 캐시의 갱신 경로와 채택 결정 시점에 관한 코드 근거다.
실제 거절 토큰 때문에 다음 단계의 전송이 늘었다는 측정 결과는 아직 없다.
캐시 오염이라는 이름을 붙이기 전에 이 손해의 존재부터 확인해야 한다.

한 페이지 의사결정 설명

1. 누가 무엇을 결정하는가?
단일 GPU에서 양자화된 MoE 전문가를 RAM에서 가져오는 실행기 개발자가,
추측 검증 중의 전문가 접근을 언제 재사용 이력으로 인정할지 결정한다.
매 접근 즉시 승격하는 기존 규칙과, 채택 결과를 확인한 뒤 승격하는 단순
대조군을 비교할 가치가 있는지가 질문이다. 가중치·정밀도·타깃 routing을
바꾸거나 전문가를 제거하는 양자화 방법을 제안하는 단계가 아니다.

예를 들어 잠정 토큰 때문에 전문가를 읽었으나 그 토큰이 거절되면,
그 접근을 재사용의 증거로 남기는 것이 다음 검증에 도움이 될 수도,
다른 전문가를 밀어내 손해가 될 수도 있다. 거절된 접근을 전부 낭비라고
세거나, 이미 퇴거한 가중치를 공짜로 복구하면 안 된다.

2. 결정 시점에 알 수 있는 정보는 무엇인가?
검증 전에는 현재 상주 전문가, 과거에 확정된 토큰의 이력, draft 입력을 안다.
각 층 실행 중 실제 routing과 cache hit/miss가 드러난다.
채택 prefix는 타깃 검증이 끝난 뒤에야 안다. 이후 단계의 routing은 모른다.
따라서 채택 마스크를 앞선 miss 처리에 미리 사용하는 정책은 비교 대상이 아니다.
채택 뒤에는 당시 남아 있는 슬롯의 이력만 바꿀 수 있으며,
이미 사라진 가중치를 다시 가져오면 전송량·시간을 모두 부담해야 한다.

3. 가장 단순하고 강한 기준선은 무엇인가?
확인한 공개 GPU 캐시는 이미 SLRU이며, 신규 항목은 probation에 두고
hit를 protected로 승격한다. 넓은 batch는 캐시를 우회하는 보호도 있다.
따라서 plain LRU만 이기는 비교는 하지 않는다.

첫 대조군은 이 구현 그대로다. 비교용 단순 수정은 채택 뒤 승격이며,
승격을 사용하지 않는 단순 삽입 규칙도 함께 보아야 한다.
추측 실행 끄기·짧은 draft도 실용적인 기준선이다.
현재 자료로 새 예측기나 학습 정책이 필요하다는 근거는 없다.

4. 기존 방법이 부족하다는 증거가 있는가?
우리의 실제 성능 관측은 없다. 다음 코드 사실만 확인했다.
- GPU 캐시는 검증 입력의 실제 전문가 집합으로 hit 승격과 miss 삽입을 수행한다.
- 토큰 채택 함수는 그 뒤에 prefix를 정하고 거절된 target KV를 제거한다.
- 검사한 함수와 GPU cache 인터페이스에는 채택 행을 되돌려 주는 연결이 없다.
이것은 조사할 실행 경로를 특정한 근거이며 버그·품질 저하·전송 손실의 증거가 아니다.

두 후보의 비교

A. 전문가 가중치와 KV의 GPU 메모리 공동 배분
VAMP는 전문가 이동·prefix 재계산·선점 비용을 비교하여 두 영역의 용량을
바꾸는 문제를 직접 다룬다. MoE-Infinity에도 adaptive memory 설정이 있다.
단일 4090에 옮기거나 기존 옵션을 다시 구현하는 것만으로 차별화되지 않는다.
현재 자료에는 이들보다 나은 결정을 요구하는 별도의 실패 조건이 없다.
결론: 넓은 공동 배분 후보 제외. VAMP의 특정 제한을 연구 전체의 공백으로
확대하지 않는다. MoE-Infinity의 설정 문서 확인은 로컬 동작 검증이 아니다.

B. 추측 검증 이후 전문가 캐시의 재사용 이력
EcoSpec은 검증 전에 채택 확률과 전문가 집합 비용으로 draft를 고른다.
MoE-SpeQ은 예측 전문가·현재 캐시·프리페치와 draft 길이를 함께 다룬다.
BigMoMo와 AcceptMoE도 채택 가능성을 고려하지만 전문가 제거를 포함한다.
따라서 “채택 가능성을 고려한다”, “출력을 보존한다”, “예측 캐싱을 한다”는
넓은 발상은 신규성이 아니다.

남겨 둔 질문은 실제 타깃 routing을 유지한 실행에서,
거절된 행으로 생긴 캐시 상태가 다음 검증들의 전송을 늘리는지다.
확인한 원문의 목적·설명과 구별되는 측정 질문이지만,
다른 모든 구현이 이를 다루지 않는다고 확인한 것은 아니다.
결론: 신규성 전망은 제한적이다. 방법 채택 대신 작은 진단에만 우선순위를 준다.

측정 가능성과 현재 부족한 자료

GPU 전송은 Helldez/llama.cpp의 고정 revision
152dd5c4a7883382509bde45ee7606433d987581에서 확인했다.
부모 실행기는 Helldez/BigMoeOnEdge
cb78bfe0f1218ab350a1b7bcd3945c45eaf94595다.
이 소프트웨어는 BigMoMo 논문의 구현으로 간주하지 않는다.

llama-moe-cache.cpp의 실제 ids 읽기 뒤와 전문가 upload 지점이 관찰 대상이다.
기존 CPU ids를 기록하는 방식을 우선하며, 계측용 routing·전문가 실행을
추가하지 않는다. 요청 순서, cache group, slot, hit, fill, eviction,
전송 바이트와 묶음 수, cache 우회 여부를 보존해야 한다.
session.cpp의 accept 뒤에서 같은 window id에 채택 길이를 연결한다.
root는 이미 확정된 행이고 그 뒤에 채택 draft가 이어진다.
EOG를 포함한 확정 행 수와 실제 외부에 출력한 토큰 수는 구분한다.

기존 route_trace의 expert_bytes는 host/flash 비용이다.
이를 GPU PCIe 전송량으로 해석하면 안 된다. 절대 token 위치는 rollback 후
재사용되므로 window id 없이 서로 다른 검증 행을 합칠 수도 없다.
기존 route trace는 graph 관찰 지점도 추가하므로 그 시간은 성능 기준이 아니다.

확인한 공개 Qwen3.8 실행 기록은 자연 routing/cache 정보는 있으나,
형식상 MTP 후보 flag가 사용되지 않고 필요한 채택·거절 branch 기록이 없다.
로컬 OLMoE의 이전 캡처에도 이 정보는 없다.
따라서 지금 가진 기록만으로 후보 B의 성능을 재계산할 수 없다.

실제 장비와 비용
- RTX 4090: 24,564 MiB. RAM 총 61.94 GiB, 확인 당시 가용 약 55.47 GiB.
- 데이터 디스크 여유 약 136.01 GiB. .git은 약 76 MiB로 삭제 조건에 미달한다.
- 로컬 OLMoE 가중치 파일 합계 12.89 GiB. 의도적으로 cache를 작게 만든
  검사는 계측 개발에는 가능하지만 실제 offload 수요의 증거가 아니다.
- 후속 실행 모델 후보는 공식 Qwen3-Next-80B-A3B-Instruct Q4_K_M 한 개다.
  공개 파일은 48,410,988,384 bytes, 약 45.09 GiB여서 24GB GPU에 통째로
  상주하지 못한다. RAM 내 실행 가능성은 아직 확인하지 않았다.
  mmap/page cache, host/device 중복, 계산 버퍼, KV와 hybrid rollback 상태를
  합친 최대량을 확인해야 한다. 작은 모델의 비트폭을 억지로 올려
  offload 문제가 생기게 만들지는 않는다.
이번 검토에서는 모델 메타데이터만 읽었고 다운로드·설치·빌드·생성을 하지 않았다.

다음 자원 배분안: 한 번의 실행 가능성 및 기록 확보 진단

이 문서는 후속 실행의 제안 범위이며 완료 기록이나 실행 등록 명세가 아니다.
지금 한 일은 후보 선택과 관찰 지점 확인까지다.

상한은 시작부터 120분, 생성 시도 최대 8회, 모델 1개, 추가 저장 최대 60 GiB다.
준비·빌드·다운로드·검증·실패한 시도도 모두 상한에 넣는다.
처음 30분 동안 코드 연결과 모델 헤더·메모리 계획을 확인한다.
4090 경로, 자연 routing, 정확한 채택 처리, 메모리 계획을 확보하지 못하면
그때 종료하며 다른 모델·backend 이식으로 우회하지 않는다.
대용량 다운로드는 이 확인 뒤에만 시작한다.

성공 시 smoke 최대 2회와 측정용 6회로 제한한다.
두 고정 입력(일반 설명 1개, 복사 성격의 입력 1개)에 대해
추측 끄기·ngram 최대 길이 1·4를 각각 한 번 실행하고 출력 상한은 128토큰이다.
추가 draft 모델이 필요 없는 ngram을 첫 진단으로 택한다.
이 선택은 ngram이 최선의 추측 방식이라는 주장과 무관하다.
입력·ngram match 설정·context·cache 예산·정확성 기준은 실행 전에 고정한다.
전문가 dropping과 임의 routing 변경은 끈다.
유효한 추측 접근이나 거절 사례가 부족하면 입력을 계속 찾아 바꾸지 않고
이번 자료로 판단 불가라고 종료한다.

계측 유효성부터 확인한다.
같은 batch 형상에서 계측 전후의 출력·routing·채택 기록을 비교한다.
원본 SLRU를 재생해 hit/miss·slot 변화·전송 바이트를 원래 기록과 맞춘 뒤에만
단순 대조 규칙을 같은 순서로 재생한다. 우회 실행을 cache miss로 꾸미지 않는다.
미래 채택 여부를 미리 사용하거나, 퇴거된 가중치를 되살리는 재생은 무효다.

이 단계의 주 산출물은 실제 전송 기록과 단순 규칙의 전송량 비교다.
거절 행의 읽기 바이트와 이후 단계에 미친 추가 비용을 구분한다.
현재 검증의 모든 필수 전송·다음 단계의 재전송을 합쳐 비교하며,
같은 전문가가 채택 행에도 필요한 경우를 중복으로 낭비 처리하지 않는다.
전송량 감소는 시간 감소의 상한이나 보장이 아니다.
DMA 묶음 수·중첩·계측 부담 때문에 별도 계측 없는 시간 검사가 필요하다.

진행·종료 판단
- 유효한 기록을 못 얻음: 실행 가능성 미확보 또는 표본 부족으로 보류 종료.
- 단순 규칙과 SLRU의 전체 전송량 차이가 5% 미만이거나 입력 간 방향이 다름:
  이 제한 조건의 정책 개발 종료. 5%는 다음 실측에 투자할 최소 신호이며
  통계적 유의성·전체 시간 이득 기준이 아니다.
- 두 입력에서 5% 이상의 전송 감소가 관측됨: 단순 수정의 계측 없는 시간
  비교 가치가 생긴다. 새 알고리즘이나 논문 기여가 확보된 것은 아니다.
- 추측 끄기·길이 축소·단순 승격 변경으로 충분하면 그 구현 결과로 닫는다.
  복잡한 선택기를 만들 필요는 없다.
실용적 속도를 주장할 때에는 각 방식이 전체 메모리 상한에서 남는 공간을
활용하는 강한 기준선과 비교해야 한다. 원인 분리용 동일 cache 용량 비교를
같은 전체 메모리 효율의 증거로 대신하지 않는다.
