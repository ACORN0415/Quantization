공개 MoE 청크 merge 커널의 제한된 GPU 재현 결과
2026-11-01, 한국 시간

결론

공개 옵션으로 가능한 네 토큰 합성 입력에서 청크 크기에 따른 FP16 결과 차이를
RTX 4090으로 재현했다. 원래 슬롯 순서를 보존하는 방법과 전문가 번호순으로
통일하는 방법도 각각 등록한 기준을 통과했다. 이 검사는 여기서 종료한다.
새 연구 방향으로 전환하지 않으며, 실제 모델의 정확도 저하를 주장하지 않는다.

기존 기준값을 반드시 보존해야 하는 실제 사용 조건과, 단순 기준선으로 감당하지
못하는 비용은 모두 확인되지 않았다. 앞선 문서의 GPU 수치 일관성 분야 전환 권고는
이번 결과로 채택하지 않는다. 산출물은 작은 회귀 검사와 정확성 요구의 설명이다.

1. 무엇을 실행했는가

공개 저장소: lcj1111/RobustGEMQ
고정 revision: fe6fe6dc679495a53795b2a7eed4efb7e655e29c
실행 파일: gemq/triton_kernels/vllm_moe_dispatch.py
원본 Git blob: 39dc86e364809b94c165e78641953bc5f7f2bc75

원본 파일과 MIT 라이선스를 tools/vendor/robustgemq_merge에 보존했다.
원본 소스는 수정하지 않았다. CUDA 커널 호출 시점의 JITFunction.run을 감싸
실제 호출 인자와 수를 기록했으며, 별도로 CUDA profiler trace를 집계했다.
계측을 위한 추가 merge 실행은 없다.

등록·CPU 기준값·실행 코드는 첫 GPU 실행 전에 ea3feff로 커밋했다.
환경은 RTX 4090 / torch 2.6.0+cu124 / Triton 3.2.0이다. 환경 변경은 없었다.
이번에는 공개 dispatch와 merge만 실행했다. 전문가 GEMM, 가중치 패킹,
전체 MoE 블록, 모델 생성, vLLM 서비스는 실행하지 않았다.

2. 실제 옵션으로 가능한 입력

토큰 수 4, top-k 8, 전문가 수 64, hidden 256, 전문가 출력·gate FP16이다.
각 토큰의 선택 전문가는 [0,2,1,3,4,5,6,7]로 중복이 없다.
gate는 [0.375,0.3125,0.25,0.03125,0.015625,0.0078125,0.00390625,0.00390625]이며 합은 1이다.
첫 토큰에 기존 반례를 넣고, 나머지 세 토큰의 전문가 출력은 모두 0으로 둔다.
같은 입력의 네 좌표 유형을 반복했다: 반례, 정확히 합산되는 대조값, 0, 반례의 음수.
작은 잔여값 반례와 FP16 반올림 경계 반례의 두 사례를 사용했다.

공개 plugin의 코드도 양의 정수 chunk_tokens를 허용하며 다음 식을 사용한다.

  assignment_limit = chunk_tokens * top_k

따라서 chunk_tokens 1/2/4는 assignment 8/16/32개에 해당한다.
총 assignment는 32개이므로 모두 유효한 분할이다. 공개 GPU dispatch가 만든
정렬 순서·역인덱스·expert offset은 별도의 CPU 계산과 일치했다.
이것은 실제 설정으로 표현 가능한 합성 merge 입력이지, 실제 양자화 모델에서
그 입력이 발생했다는 증거나 서비스 전체를 실행했다는 증거는 아니다.

3. 주 결과: 두 번째 반례의 첫 토큰·첫 좌표

경로                               chunk_tokens=1     =2             =4
공개 청크 merge                    1.0009765625       1.0            1.0
전체 출력 보관 후 원래 슬롯 합산    1.0                1.0            1.0
전문가 번호순으로 슬롯·gate 통일    1.0009765625       1.0009765625   1.0009765625

모든 경로는 같은 전문가 출력·gate·선택 전문가를 사용했다.
두 번째 방법은 들어오는 청크를 전체 버퍼에 복사한 뒤 원본 merge를 한 번 호출한다.
세 번째 방법은 역인덱스와 gate의 슬롯을 전문가 번호순으로 함께 정렬한다.
어느 방법도 원본 merge 커널의 코드를 변경하지 않았다.

2사례 × 3경로 × 3청크 설정 × 2회 = 36개 전체 출력 배열을 검사했다.
각 배열은 형상·dtype·모든 원소 바이트가 해당 경로의 CPU 기준값과 일치했다.
실행 순서를 바꾼 반복 18쌍도 전체 비트 일치했다. 최종 첫 좌표만 비교한 검사가 아니다.
다만 이 작은 입력 집합에서의 결과를 모든 입력의 동일성 증명으로 확대하지 않는다.

4. 재현성과 수학적 정확성은 다른 판정이다

두 번째 반례의 정확한 실수 합은 다음 유리수다.

  16785413 / 16777216 = 1.000488579273223876953125

이를 FP16으로 최근접·동점 짝수 반올림하면 1.0009765625다.
따라서 이 사례의 청크 1 결과와 전문가 번호순 결과가 올바르게 반올림한 값과 같다.
기존 슬롯 순서의 1.0을 재현했다고 해서 수학적으로 더 정확한 것은 아니다.
반대로 이 사례에서 전문가 번호순이 더 정확했다고 모든 입력에서 더 정확하지는 않다.

검사 기준을 세 가지로 분리했다.

  원래 슬롯 기준: 원래 top-k 순서의 FP32 누산 뒤 FP16 변환과 비트 일치하는가?
  전문가 번호순 기준: 정해진 다른 합산 순서와 비트 일치하는가?
  실수 합 기준: FP16 입력의 정확한 유리수 합을 FP16으로 올바르게 반올림한 값인가?

첫 기준은 과거 결과 재현에 관한 요구다. 셋째는 해당 합산의 수학적 정확성 요구다.
공개 merge 단위 검사는 첫 기준의 정확한 FP16 일치를 검사한다. 이번 반례는
그 고정된 무작위 사례 밖에서 같은 판정식이 실패하는 유효한 입력을 제공한다.
공개 단위 검사의 기존 무작위 사례를 이번에 다시 실행한 것은 아니다.

모델 보고서에 제시된 atol=0.002, rtol=0.002 숫자를 이번 merge 출력과 원래 슬롯
기준값에 적용하면 36개 모두 통과했다. 이것은 merge 수준의 참고 검사일 뿐이다.
모델 수준의 회귀 기준이나 서비스 품질을 통과·위반했다는 결론은 내리지 않는다.

5. 단순 기준선의 비용을 어디까지 확인했는가

이 검사에서 전체 전문가 출력은 32 × 256 × 2 = 16,384바이트다.
슬롯 보존 경로는 같은 크기의 추가 버퍼와 실제 청크 복사를 사용했다.
전문가 번호순 경로에는 정렬과 역인덱스·gate 재배치가 필요하다.
그 준비는 실제 GPU에서 수행했지만 정렬을 두 반례에 재사용했다.
이를 비용이 없는 방법이나 같은 실행 시간이라고 표현하지 않는다.

이번 입력은 GPU에 전체 출력 fixture를 공통으로 보관한다. 기록된 tensor payload와
프로세스 peak는 실제 스트리밍 배포의 메모리 비교가 아니다. 컴파일·profiler·동기화를
포함한 실행이므로 경로별 성능 우위도 주장하지 않는다.
단순 기준선이 실제 메모리 상한 또는 시간 목표를 충족하지 못한다는 관측은 없다.

6. 실행 기록과 상한

전체 시작: 2026-11-01 00:32:46 KST
전체 상한: 2026-11-01 01:32:46 KST, 준비·실행·감사·보고 포함
GPU 단계 상한: 300초, 실제 측정 1.1624초
merge 상한: 100회, 실제 68회

실제 merge 호출: 공개 경로 28회 / 슬롯 보존 12회 / 전문가 번호순 28회
공개 dispatch: count 1회 / scatter 1회
호출 위치 기록과 CUDA trace의 대상 커널 집계가 모두 일치했다.
이는 대상 커널의 호출 수이며 PyTorch의 나머지 CUDA 연산을 포함한 전체 호출 수가 아니다.
무효·미완료 실행 0회, 모델 forward 0회, GPU 재실행 0회.
정확한 전체 완료 시각과 경과시간은 completion.json에 기록한다.

7. 보존과 감사

result.json: 모든 판정, 실행 환경, 자원 기록
calls.json / cuda_trace.json: 호출 지점 기록과 실제 GPU trace
raw/: 입력 8개와 출력 36개의 전체 원소 바이트
raw_manifest.json: 형상·dtype·파일 해시
cpu_reference.json: 정확한 유리수 합과 실행 전 CPU 예측
audit.json: 저장된 원소 전체를 독립 NumPy/Fraction 계산으로 재검증한 결과
source_audit.json: 실제 옵션과 정확성 요구를 확인한 고정 코드·문서

감사에서는 원본 소스 blob, 등록·코드 해시, 원자료 44개, 출력 36개, 반복 18쌍,
실제 CUDA 호출 수를 재확인했다. 감사용 GPU 실행은 없다.
재현 코드는 tools/reproduce_moe_chunk_merge.py, 저장 자료 감사 코드는
tools/verify_moe_merge_record.py다. 등록한 실행 시간창은 원래 실험을 보호하기 위한
검사이므로, 시간창이 지난 후 새 실행은 별도 복사본과 새 등록 시각으로 수행해야 한다.

이번 종료 판단

합산 순서에 따른 결과 차이는 재현됐다. 두 단순 방법은 서로 다른 수치 요구를
충족했다. 기존 슬롯 기준값 보존의 실제 필요성과 단순 방법의 감당하기 어려운 비용이
확인되지 않았으므로, 새 방법 개발이나 전체 모델 실험으로 확대하지 않는다.
이 결과를 회귀 검사와 요구 명세의 구체화로 보존하고 마무리한다.
