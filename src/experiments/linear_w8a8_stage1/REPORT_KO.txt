A안 결과 — 초기 청크 linear 비용과 단순 PyTorch W8A8
2026-11-04

판단
시험한 세 실제 형상에서는 정확성 검사를 통과한 단순 W8A8 경로가 BF16보다 약 3.01~4.01배 느렸다.
따라서 이 경로를 전체 영상 모델에 적용하는 다음 단계로 진행하지 않는다. 이 작은 실행 진단은 완료한다.
최적화된 fused W8A8, 기존 diffusion 양자화 커널, 다른 형상·GPU까지 기각한 결과는 아니다.
새 논문 기여나 가중치 양자화 연구 전체의 종료를 주장하지 않는다.

무엇을 실제로 실행했는가
- RTX 4090 24GB, PyTorch 2.6.0+cu124, 기존 Self-Forcing EMA와 QVG 고정 revision.
- 첫 프롬프트, seed303, batch1, 과거 KV 없는 초기 3 latent frame, M=4680.
- 모델 1회 실행에서 4 denoise + 1 cache-record, forward 시작/완료 각 5회.
- VAE 실행 및 최종 영상 생성·평가는 하지 않았다. 텍스트+모델 준비 55.27초는 별도 구간이다.
- 모든 nn.Linear를 계측했다. forward index1~4의 leaf event 시간 합으로 상위 3개 형상을 선택했다.
  같은 형상의 모든 모듈 입력을 대표하지는 않는다. 각 형상에서 index1에 처음 만난 모듈 입력 하나를 사용했다.
  세 캡처는 모두 block0, denoise timestep937.5의 입력이다. 정확성 결과는 이 입력 범위에 한정한다.
- 형상별 BF16/W8A8 warmup 각10회, 10개 대응 round×경로당10회. 두 경로의 순서를 교차했다.
  총 타이밍 호출600회, warmup60회이며 정수/출력 정확성 호출은 이 수와 별개다.

음수 감소율은 느려졌다는 뜻이다. 대응 비율 기준 실행시간 배수는 3.008, 3.359, 4.005배다.
구간은 10개 타이밍 블록을 재표집한 구간이지 서로 다른 입력·프롬프트에 대한 일반화 구간이 아니다.
등록한 >=5% 시간 감소 및 구간 하한>0 기준을 통과한 형상은 0개다.

정확성과 품질 범위
- 작은 유효 정수 형상 3사례의 INT32 출력 전 원소가 CPU INT64 합산과 같았다.
- 실제 형상에서는 등록한 첫/마지막8행×첫16출력의 정수 결과를 확인했고 범위·누산 상한을 충족했다.
  이 부분 검사를 전체 INT32 출력 검증으로 확대하지 않는다.
- 같은 양자화 정수의 별도 FP32 GEMM은 실행 중 전체 INT32 결과를 FP32로 변환한 값과 최대 차이0이었다.
- 최종 BF16과 양자화 FP32 참조의 relative-L2는 0.1646%, 0.1659%, 0.1658%였다.
  등록한 relative-L2<=0.2% 및 원소별 허용오차, finite·shape·dtype 검사를 모두 통과했다.
- 원래 모듈의 캡처 BF16 출력과 native F.linear 재실행은 실행 중 전 원소 바이트가 같았다.
- 원래 BF16 출력 대비 W8A8 relative-L2는 각각 0.5535%, 1.1847%, 0.5423%다.
  5% 공학적 선별 기준을 통과했다는 뜻이며 영상 품질 동등성이나 전체 모델 오차 보장은 아니다.

메모리와 준비 비용
역할                 BF16 추가 peak MiB  W8A8 추가 peak MiB  공통 상주 MiB  W 정적 준비 ms
Q 투영                   15.000               91.399              43.384          6.453
FFN 확장                 81.000              486.908             141.551          0.724
FFN 축소                 14.711              480.018             141.509          0.768

이는 매 경로 직전에 peak를 초기화한 PyTorch allocated 증가량이다. 전체 프로세스 실측 peak가 아니다.
두 경로는 같은 입력·출력 참조·BF16 W·양자화 W가 공존하는 동일 상주 상태에서 측정했다.
W8A8 가중치 payload+FP32 scale만 보면 Q는 4.5MiB→약2.256MiB, FFN은 26.25MiB→약13.13~13.16MiB다.
bias와 공통 입력·출력은 이 가중치 저장량에서 제외한다. 가중치가 작아져도 임시 INT32/FP32 배열 때문에
실행 peak는 증가할 수 있음을 이번 구현에서 확인했다. 모델 전체의 배포 메모리 절감으로 환산하지 않는다.
W 준비는 한 번의 관측이며 첫 호출의 초기화 비용이 섞일 수 있다. 경로 간 steady-state 비교 지표로 쓰지 않는다.

왜 단순 구현은 충분하지 않았는가
이번 W8A8은 W를 사전에 INT8로 바꾸고, 매 호출 X 행별 양자화→INT8 GEMM→INT32 출력→FP32 scale
적용→bias→BF16 저장을 별도 PyTorch 연산으로 수행한다. 모든 동적 비용을 시간에 포함했다.
코드에서 큰 중간 배열이 생기는 것을 확인했고 실제 peak 증가도 관측했다. 다만 세부 단계별 시간은
따로 계측하지 않았으므로 어느 한 단계가 지연의 몇 %를 차지한다고 단정하지 않는다.
MixLLM 같은 시스템 논문의 융합·파이프라인 설계 필요성과 부합하지만 그 커널을 시험한 것은 아니다.

linear는 실제로 큰 비용이었는가
첫 forward CUDA event는 329.40ms, 이후 네 forward는 161.61~162.73ms였다.
이후 네 forward의 leaf-linear event 합은 각각 73.80~73.98ms였다.
독립적으로 Chrome trace의 cat=kernel 항목만 합산하면 이름에 gemm이 들어간 커널은 364.85ms,
FlashAttention forward 커널은 162.54ms였다(전체5forward).
이름 기반 커널 분류이며 CPU op와 자식 CUDA kernel을 중복 합산하지 않았다. memcpy·CPU 공백은 제외한다.
측정된 최초 청크에서 GEMM 비용이 무시할 수준은 아니다. 다만 모델 profiler·hook·캡처가 교란한
wall time은 1.686초였고, 커널 시간 합이나 leaf 시간 비율은 전체 생성의 가속 상한이 아니다.
긴 문맥에서는 attention 비용과 비중이 달라진다. 기존 12청크 프로파일과 같은 조건이라고 비교하지 않는다.

실행 유효성·실패·감사
등록/코드 커밋 090b8e1 이후 첫 사전 정수 검사의 M=8 제약 위반을 수정했다(4e6600d).
실패 원문은 attempt1에 보존했다. 이때 모델 forward와 실제 형상 타이밍은 모두0회였으며,
M=32로 고친 뒤 한 번의 모델 실행만 했다. 후보·오차 기준·전체60분 상한은 유지했다.
등록 시작22:10:04 KST, GPU 진단 완료22:23:17.50 KST, 준비 포함13분13.50초로 상한 내 완료했다.
CPU 감사는 GPU를 사용하지 않고 입력 파일 해시·형상·finite·선택 순위·대응 시간·구간·판정을 재계산했다.
각 캡처의 CPU FP64 정수 행렬곱과 FP64 norm 기반 출력 재구성도 저장된 GPU 상대오차와 1e-6 이내로 맞았다.
첫 CPU 감사의 FP32 norm 합산 문제는 실패 로그와 CPU_AUDIT_CORRECTION_KO.txt에 분리해 기록했다.
측정 코드를 바꾸거나 등록 허용오차를 느슨하게 만든 것이 아니다.
GPU W8A8 출력 배열 자체는 저장하지 않았으므로 CPU 감사가 그 원소 바이트까지 재확인한 것은 아니다.
원래 BF16 replay의 바이트 일치도 실행 시 검사 기록에 근거한다. 원시 X/W/bias/Y와 trace는 보존했다.
