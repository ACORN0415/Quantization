[A] 허용되는 결론의 경계 (과장 방지, 가장 중요)
  말할 수 있는 것: "torch._int_mm 기반 unfused PyTorch W8A8 경로는 이 세 형상에서 BF16 cuBLAS보다 3–4배 느리고
  임시 peak가 6–33배 크다. 이 구현으로는 이득 없음." 등록 명세의 종료 문구 그대로다.
  말할 수 없는 것: "4090에서 INT8/W8A8은 이득이 없다", "linear 양자화 방향 종료".
  근거(계산 추정, 측정 아님): 초과 시간은 INT8 GEMM이 아니라 FP32 elementwise pass가 설명한다.
   - quantize()는 x.float()로 X 전체를 FP32 복사한 뒤 amax/div/round/clamp/int8 변환을 별도 커널로 수행(:193–:196).
     ffn.2(K=8960)의 X FP32 사본은 4680×8960×4 B ≈ 168 MB, 6회 pass ≈ 1.4–1.6 GB 트래픽 ≈ 1.5 ms @≈1 TB/s.
     측정된 초과 3.135−0.783 = 2.35 ms와 크기가 맞는다.
   - ffn.0(N=8960)은 반대로 acc.float()*sx*sw.t()+bias→bf16의 M×N FP32 pass 5회(:226–:229)가 ≈168 MB씩 → ≈1.5 ms.
     측정 초과 1.88 ms와 맞는다.
   - BF16 기준선 자체가 이미 높은 처리량이다: 2·4680·8960·1536 = 128.8 GFLOP / 0.794 ms ≈ 162 TFLOPS,
     1536² 형상 ≈ 155 TFLOPS. 사양상 Ada BF16(FP32 누산) dense 피크 근처(사양 수치는 기억 기반, 문서 재확인 필요).
     따라서 INT8 GEMM만 바꿔도 절약 가능한 시간은 GEMM 시간의 일부(≤0.4–0.6 ms/call)이고,
     이 경로가 추가한 1.9–2.4 ms 오버헤드가 그보다 훨씬 크다. 결과는 "fused epilogue 없는 구현"에 종속된 것이다.
  주 작업자 보고서는 G3 식 T_new/T_old≈(1−p)+p/s+h에서 h가 p/s 이득을 압도했다고 쓰면 정확하다.

[C] 검사 3(quantized reference rel_l2≤0.002)은 사실상 BF16 반올림 바닥을 측정한다
  세 형상 모두 0.00165–0.00166이다. 같은 FP32 값을 BF16으로 반올림할 때 기대되는 상대 L2는
  ≈0.577·2^-8·E[1/mantissa] ≈ 0.0016(계산 추정)이며 측정값과 일치한다. 즉 검사 3은 "후보의 FP32 수식이 참조와 같고
  마지막에 BF16으로 반올림했다"만 확인하며, 문턱 0.002는 여유가 0.00035뿐이다. 이 통과를 "구현 정밀 일치"로 서술하지 말고,
  정수 경로의 실질 증거는 fp32_integer_reference_max_abs=0.0(전 원소)과 CPU FP64 재구성 일치로 제시할 것.
  8×16 표본 INT64 검사는 코드가 integer_sample_shape로 표기했으므로 전체 검사로 쓰지 않으면 된다.

[H] 공정성에서 확인한 사소한 점
  - 정적 W 준비 시간은 실행 시간에서 제외(등록대로). 6.45 ms는 첫 형상 cold 값이므로 형상 비용으로 쓰지 말 것.
  - 기준선 F.linear는 bias를 cuBLAS epilogue로 융합하고 후보는 별도 add — 이는 "단순 경로"의 정의에 포함되며 불공정은 아니다.
    다만 [A]의 이유로 결과의 일반화 한계가 된다.
  - TF32 비활성화는 FP32 참조 GEMM에만 의미가 있다(BF16 GEMM 무관). FP32 참조는 부분합이 2^24 미만일 때만 정확하므로
    max_abs=0.0은 "강한 전원소 증거"이지 수학적 증명은 아니다(코드 주석 :238–:239가 이미 명시).
  - CPU 감사의 FP32→FP64 norm 변경은 감사 지표의 정밀도 수정이며 실험 기준 변경이 아니다(CPU_AUDIT_CORRECTION_KO.txt). 타당.
