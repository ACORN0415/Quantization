  비교해 eager BF16의 오차와 같은 수준인지로 판정하는 방식이 가장 싸다. CPU만으로 가능하다.

2. 실제 융합/정수 버퍼 (shape0 출력 코드 inductor/ax/caxlhov….py와 trace.json 직접 확인; shape1도 동일 구조)
- fused 팔은 커널 3개: Triton reduction(양자화, qx int8+sx) → Triton 템플릿 triton_tem_fused__to_copy_clamp_clamp_min_div_mul_round_1
  (int8 tl.dot, ACC int32, BLOCK 256x128x128, 에필로그 acc*sx를 FP32로 저장) → Triton pointwise(×sw, +bias, BF16 변환).
  extern_kernels._int_mm 호출 없음, INT32 버퍼 없음, ampere_igemm 커널 trace에 없음. 등록된 '융합 발생' 조건은 충족한다.
- 그러나 INT32 M×N 버퍼는 같은 크기의 FP32 M×N 버퍼(buf3)로 대체됐다. 추가 allocated peak는 43.74MB로 default 43.76MB와 같다.
  sw/bias/BF16 변환은 GEMM 에필로그에 들어가지 않았다. 따라서 '정수 중간 버퍼 제거'는 문자 그대로는 맞지만 메모리 이득은 0이고,
  메모리 트래픽 관점에서도 sx 곱 융합 자체는 바이트를 줄이지 않는다.
- 이득의 원천은 융합이 아니라 GEMM 커널 교체다. 설치된 torch 2.6.0 kernel/mm.py 285~330행: tuned_int_mm은 Triton 템플릿이
  가능하면 ATen _int_mm 후보를 버린다("TODO: Re-enable eager mode implementation once cuBLAS is fixed"). 773~800행:
  tuned_fused_int_mm_mul은 Triton 후보만 가진다. 즉 max_autotune_gemm=True만으로도 cuBLAS igemm은 후보에서 빠지고 Triton int8
  템플릿이 선택된다. 로그의 AUTOTUNE int_mm(4680x1536, 1536x1536) 독립 템플릿 0.0932ms, 융합 에필로그 포함 0.1085ms(동일
  256x128x128 config)이며 A-1이 잰 cuBLAS igemm GPU 시간은 .16589ms였다. 설계에 'W8A8 + max_autotune_gemm, force_fuse 없음'
  팔이 없어서 force_fuse_int_mm_with_mul 고유의 기여는 분리되지 않았다. 보고서에서 "GEMM+scale 융합으로 빨라졌다"로 쓰면 과장이다.
  "autotune이 선택한 Triton int8 GEMM(scale 에필로그 포함)이 cuBLAS igemm보다 빠른 형상이 있다"가 정확한 서술이다.
