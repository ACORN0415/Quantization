MoE 후속 두 후보 검토와 다음 자원 배분
조사 시작: 2026-10-31, 기록 마감: 2026-11-01 (한국 시간)

판단

새 양자화 알고리즘으로 채택할 후보는 이번에도 없다. 다만 다음 행동까지 정한다.
양자화 목적함수에 변수를 추가하는 탐색은 중단하고, 인접 분야인 GPU 실행의
수치 일관성 검증으로 이동하는 것을 권고한다. 첫 대상으로 아래 B의 구체적인
청크 합산 경로를 선택한다. 다음 자원은 최대 60분의 공개 커널 재현과 단순
기준선 검증에만 배정한다. 새 커널 최적화, 모델 품질 실험, RL 실험은 배정하지 않는다.

이는 논문 주제 확정이 아니다. CPU에서 확인한 현상을 실제 구현에서 확인하고,
기존의 간단한 해결책으로 충분한지를 판단하는 진입 검사다. GPU 검증 분야에도
Vosti와 커널 검사기 분석 등 가까운 연구가 있으므로, 분야를 바꾸었다는 이유로
신규성을 주장하지 않는다. 종료한 교차항 배분 후보는 그대로 종료 상태다.

A. 정밀도가 다른 MoE 전문가의 실행 비용

누가 무엇을 결정하는가
  추론 구현자가 기존 mixed-bit 가중치를 전문가별로 실행할지, 묶어서 실행할지 결정한다.
  선택 시점에는 packed 형식, 전문가별 비트폭, 토큰 수, routing과 GPU 자원을 알 수 있다.

이미 있는 근거
  [문서·코드 확인] GEMQ의 OLMoE 다중 토큰 경로는 활성 전문가를 순회하며
  전문가당 세 번의 양자화 GEMM을 호출한다. README도 prefill 병목을 명시한다.
  [우리 실측 아님] 우리 4090에서 해당 GEMQ 경로의 시간을 재측정하지 않았다.

가까운 기존 방법과 가장 단순한 강한 기준선
  RobustGEMQ는 이미 variable-M mixed-bit grouped GEMM, gate/up/activation 융합,
  workspace 제한 청크 실행, GPU dispatch를 제공한다. 원래 Python 반복문만을
  기준선으로 새 성능 기여를 주장할 수 없다.
  MxMoE는 정밀도별 계산 특성을 고려한 배분과 이질적인 Group-GEMM 생성까지 다룬다.
  입력 분포를 이용한 커널 선택도 DA-MoE와 겹친다.

남은 부분과 실행 가능성
  기존 최적화 뒤에도 비용이 남는다는 것과, 우리가 해결할 미해결 문제가 있다는 것은
  다르다. 현재 자료에는 강한 mixed-bit 기준선이 우리 조건에서 실패한다는 관측이 없다.
  RobustGEMQ의 확인된 서비스 환경과 현재 환경도 다르다. 4090 이식 성공은 미검증이다.

선택
  단순 반복문 제거·혼합 비트 묶음 실행·일반적인 적응 커널 선택을 새 연구로 채택하지 않는다.
  원래 GEMQ보다 빨라지는지를 보기 위한 새 GPU 실험도 실행하지 않았다.

B. workspace 청크 변경과 MoE 합산 결과의 일관성

누가 무엇을 결정하는가
  추론 구현자가 메모리 상한에 맞춰 전문가 출력을 나누어 계산할 때,
  어떤 합산 순서와 정확성 기준을 유지할지 결정한다.
  선택 시점에 알 수 있는 것은 dtype, routing, 원래 합산 순서, packed 형식,
  입력 형상과 workspace 상한이다. 최종 생성 품질을 보고 기준을 바꾸지 않는다.

가까운 선행연구
  vLLM의 train-inference consistency 작업과 Megatron의 batch-invariant MoE 구현은
  이미 라우팅·전문가 연산·합산 순서의 일관성을 다룬다. Vosti는 배치·청크·캐시
  변화에 대한 시스템 수준 명세와 검증을 제공하고 MoE 확장도 논의한다.
  따라서 'MoE를 결정적으로 실행하자'는 넓은 주제는 신규성이 부족하다.

좁힌 조건
  RobustGEMQ의 확인한 merge 경로는 전문가 번호로 정렬된 assignment를 여러 청크로
  나눈다. 각 청크에서는 원래 top-k 슬롯 순서로 순회하되, 현재 청크 밖의 항을
  제외하고 FP32 누산값을 다음 청크에 넘긴다.
  이 구조에서 '각 청크 안의 슬롯 순서 고정'은 '청크 크기가 바뀌어도 전체 슬롯
  합산 순서 유지'를 뜻하지 않는다. 고정 설정에서의 반복 재현성과도 다른 요구다.

직접 확인한 것
  [CPU 합성 반례] FP16 전문가 출력과 FP16 gate, FP32 누산, 마지막 FP16 변환을
  사용한 두 사례에서 청크 크기에 따라 값이 달라졌다. 두 번째 사례는 다음과 같다.

    같은 입력과 gate, 전체 슬롯 순서 유지: 1.0             (FP16 bytes 003c)
    같은 입력과 gate, assignment 2개씩:   1.0009765625    (FP16 bytes 013c)

  비트열 표기는 little-endian이다. 선택된 전문가는 중복이 없고 gate 합은 1이다.
  이 반례는 실수 덧셈의 비결합성이라는 알려진 성질을 구체적 코드 흐름에 적용한 것이다.
  CUDA 커널을 실행한 결과, 품질 저하, 다음 층 routing 변경, 신규성의 증거는 아니다.

  [기존 routing의 CPU 구조 검사] OLMoE의 기존 24문서·12,288토큰에서
  assignment 1,024개씩 나누면 12,265토큰의 유효 합산 슬롯 순서가 바뀐다.
  128개 또는 512개씩이면 12,287토큰, 전체 4,096개를 한 번에 처리하면 0토큰이다.
  이는 순서 변화의 수이며, 출력 불일치 토큰 수가 아니다.
  이 routing은 이전 BF16 캡처로, RobustGEMQ 양자화 모델이나 서비스 트래픽이 아니다.
  여기서 청크 크기는 assignment 수다. 공개 코드의 chunk_tokens는 top_k를 곱하므로,
  이 모델에서 assignment 1,024개는 chunk_tokens=128에 해당한다.

가장 단순한 강한 해결책
  1. 같은 토큰의 top-k 출력을 보관한 뒤 원래 슬롯 순서로 합산한다.
     기존 기준값 보존에 대한 직접적인 기준선이다. 메모리·전송 비용을 포함해야 한다.
  2. 토큰을 기준으로 청크를 나누고 한 토큰의 top-k를 함께 처리한다.
     합산 순서를 보존할 수 있다. 전문가 GEMM의 타일·반올림까지 같다는 보장은 별도다.
  3. 전문가 번호순을 새로운 공통 합산 규칙으로 정한다.
     CPU의 두 반례에서는 모든 청크 크기가 같아졌다. 그러나 원래 슬롯 순서의 값과는
     달랐다. 새로운 공통 규칙을 허용하는 요구에서는 이것부터 비교해야 한다.
     원래 기준값 보존이 필요하다는 이유를 먼저 제시하지 않고 이 방법을 제외하면 안 된다.

현재 부족한 근거
  현재 512토큰·top-8·hidden 2,048 조건에서 FP16 전문가 출력 전체는 16 MiB다.
  이는 출력 버퍼만의 크기이며 전체 workspace나 GPU peak가 아니다.
  이 작은 조건에서 직접 보관 기준선이 메모리 때문에 불가능하다는 증거는 없다.
  현재 원문·코드 확인만으로 RobustGEMQ가 모든 청크 크기의 비트 일치를 약속했다고
  판단하지도 않는다. 그 프로젝트의 허용오차 기준에서는 위 차이가 허용될 수 있다.
  따라서 현 단계에서 구현 버그, 품질 손상, 논문 기여라고 부르지 않는다.

한 페이지 자원 배분 결정

  다음 작업: GPU 실행의 수치 일관성 검증으로 이동하기 위한 단일 진입 검사.
  대상: 고정 revision의 공개 merge 커널 한 개와 위 단순 기준선들.
  상한: 준비·실행·유효성 확인·보고를 포함해 60분, GPU 사용 최대 5분,
        직접 계측한 대상 merge 호출 최대 100회, 모델 forward 0회.
        어느 상한이든 먼저 도달하면 종료한다. 기존 환경은 변경하지 않는다.

  먼저 할 일:
    같은 합성 입력을 실제 공개 커널에 전달해 CPU가 예측한 차이가 재현되는지 확인한다.
    source hash, 실호출 수, dtype, 입력·출력 비트열과 실행 순서를 기록한다.
    원래 슬롯 순서 유지와 전문가 번호순 통일을 서로 다른 정확성 계약으로 구분한다.
    작은 실제 입력을 확보하기 전 합성 반례를 발생 빈도나 모델 영향으로 확대하지 않는다.

  검사 성공:
    실제 커널에서 구조상 차이를 확인하고 단순 기준선의 출력 계약을 확인한다.
    성공해도 이는 회귀 검사·명세 보완의 근거이며, 새 알고리즘의 성공이 아니다.
  검사 실패/판단 불가:
    CPU와 GPU가 다르면 FMA·컴파일·호출 조건부터 상한 안에서 확인한다.
    실행 경로를 확보하지 못하면 이식 연구를 시작하지 않고 실행 미확보로 끝낸다.
  연구로 확대할 조건:
    실제 필요한 조건에서 기존 기준값 보존이 요구되고, 단순 기준선이 실제 메모리 상한
    또는 명시된 시간 목표를 충족하지 못한다는 별도 관측이 있어야 한다.
    이 조건은 현재 충족되지 않았다. 단순 기준선이면 충분할 경우 검증 도구로 정리한다.

이 선택의 이유

  현재 장비는 단일 24GB GPU이며, 우리가 가진 강점은 입력·상태·수치 경로를 분리한
  검증과 원인 해석이다. 일반적인 비트 배분·교차항·커널 선택 제안은 직접적인 선행연구와
  강한 단순 기준선에 막혔다. 같은 양자화 후보를 더 낮은 비트나 다른 층으로 늘리는 것보다,
  실제 실행이 어떤 수치 계약을 만족하는지 검증하는 인접 작업이 현재 자원에 맞는다.
  이것은 양자화 분야 전체에 공백이 없다는 판단도, GPU 검증 분야의 신규성을 확보했다는
  판단도 아니다. 다음 60분을 어디에 쓸지에 대한 결정이다.
