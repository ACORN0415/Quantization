MoE 배분 선택 검사: 기준선 확정과 CPU 검증
2026-10-31

판단: 다음 자원은 한 층의 작은 배분 선택 검사에만 쓴다.
교차항을 새 방법으로 채택한 상태가 아니다. 이번에 끝낸 것은 원문·코드 확인,
A/B/C 비교 명세와 CPU 계산 검증이다. 실제 모델의 오차·품질·가속은 아직 측정하지 않았다.
새 GPU 호출, 모델 forward, 가중치 다운로드, 기존 환경 변경은 모두 0이다.

1. 무엇을 결정하는 검사인가

배포 전에 전문가별 저장 정밀도를 고르는 사람이, 같은 저장 예산에서
개별 손상의 합만 보고 골라도 되는지 판단한다. 보정 입력·실제 routing·양자화
후보는 사용할 수 있지만, 선택할 때 보류 입력의 결과는 사용하지 않는다.

A는 mean_t sum_e ||g_e delta_e||^2를 최소화한다. gate는 제곱으로 들어간다.
B는 mean_t ||sum_e g_e delta_e||^2를 최소화한다. 전문가 출력을 재사용하고,
변경된 전문가의 토큰 행에 대해서만 잔차와 제곱 노름을 증분 갱신한다.
C는 같은 B 목적함수를 사전 계산한 내적으로 평가한다.
B와 C의 선택 차이는 품질 기여가 아니라 먼저 조사할 수치·구현 문제다.

모든 경로의 후보·시작점·사전순 방문·평가 수·동점 규칙은 같다.
B에도 토큰 묶음 단위 처리와 캐시 재사용을 허용한다. B를 매번 전체 전문가를
재실행하는 느린 기준선으로 만들거나, 전체 데이터의 오차를 상주시킬 이유는 없다.

2. 기존 근거가 답한 것과 남은 것

DPA-MoE 부록 B의 59.8%와 Spearman 0.999–1.000은 원문에서 확인했다.
여기서 k=2는 선택 전문가 수가 아니라 정밀도 청크 수다. 표는 정밀도를
고정하고 서로 다른 dispatch의 오차 순위를 비교한다. 같은 입력에서 같은
바이트의 여러 혼합 배분 중 선택이 달라지는지는 그 표의 직접 측정 대상이 아니다.
그 공백이 실제 손해를 만든다는 증거는 아직 없다.
출처: https://arxiv.org/html/2610.21378v1#A2

우리 첫 검사는 OLMoE-0924와 일반 RTN을 쓴다. SharedScale AnyBCQ와
OLMoE-0125 등을 사용하는 DPA 전체 방법의 재현이나 반례로 부르지 않는다.
SFMoE 등의 결합 평가와 비교해 신규성이 확보됐다는 결론도 아직 하지 않는다.

3. 작은 실제 검사로 고정한 범위

모델: allenai/OLMoE-1B-7B-0924, revision 6d84c48581ece794365f2b8e9cfb043c68ade9c5.
대상: 0부터 세는 8번 MoE 층 하나, 전문가 4개. 나머지 60개는 BF16이다.
전문가 선택: 보정 입력의 gate 가중 공동 선택 빈도만 사용한다. 가장 큰 쌍에서
시작해 연결 가중치 합이 큰 전문가를 추가하며, 동점은 작은 번호를 우선한다.
양자화 오차나 보류 입력을 보고 전문가·층을 고르지 않는다.

입력: WikiText2 train의 8개 문서, validation의 다른 16개 문서, 문서당 512토큰.
데이터 revision은 고정했고 실제 문서·토큰 선택은 아직 하지 않았다.
실행 전 문서 번호·해시·토큰 구간을 동결한다. 선택용과 검증용 문서를 재사용하지 않는다.
실제 BF16 MoE 입력과 routing을 고정한다. 이 모델은 norm_topk_prob=false이므로
top-8 gate를 임의로 다시 정규화하면 안 된다.

코덱: 그룹 128의 affine RTN, 전문가의 세 projection에 같은 비트폭을 사용한다.
후보: 네 전문가에 {2,3,3,4}비트를 배치하는 12개 순열을 전수 평가한다.
이 12개 안의 보정 목적함수 최솟값만 말할 수 있다. 전체 MoE의 최적 배분은 아니다.

저장량에서 찾은 주의점: GEMQ의 해당 패킹은 3비트 값을 32비트 워드에 10개씩 넣는다.
따라서 명목상 평균 3비트라고 실제 바이트가 같은 것은 아니다.
CPU 참조 형식의 code+scale+zero 실할당 바이트는 전문가당 다음과 같다.
  2비트: 1,769,472 / 3비트: 2,719,744 / 4비트: 3,342,336
12개 후보는 각각 10,551,296바이트(10.0625 MiB)다.
반면 {3,3,3,3}은 327,680바이트 더 크므로 동일 예산 기준선으로 섞지 않는다.
이는 참조 형식의 payload이며 파일 컨테이너·기타 배포 메타데이터·공통 BF16
가중치는 별도다. 실제 모델에서 추가 상태까지 세어 후보별 바이트가 같음을 확인한다.
출처: https://github.com/jndeng/GEMQ/blob/5eb2240cb46d9811bc9f79026100b46f62a7b642/gemq/triton_kernels/utils.py#L74

첫 검사는 패킹한 RTN 가중치를 복원해 BF16 전문가 출력을 얻는 국소 진단이다.
GEMQ의 Triton 정수 추론 성능을 재현하거나 압축 상태의 추론 가속을 측정하지 않는다.
정수 코드·메타데이터·복원 가중치의 왕복 검증을 실제 모델에서 먼저 통과해야 한다.

4. 지금 직접 검증한 것

tools/moe_allocation_objectives.py에 A, 잔차 증분 B, 교차항 C와 참조 패킹을 구현했다.
tools/verify_moe_allocation_baselines.py를 CPU에서 실행했다.
합성 29사례 × 12후보 = 경로별 348개 점수에서 B/C가 별도의 직접 합산과
atol=1e-10, rtol=1e-9 안에서 일치했다. 29사례 모두 B/C/참조의 선택도 같았다.
희소 routing, 고정된 나머지 오차와의 교차항, 상쇄, 동점, 역순 방문,
입력을 나누어 계산한 결과의 합산을 포함했다. 전문가가 함께 선택되지 않는
사례에서는 A와 B도 같았다. 합성 상쇄 사례의 A/B 차이는 실제 모델 증거가 아니다.
2/3/4비트의 꼬리 길이 30조건에서 패킹을 검사했고 실제 전문가 행렬 형상의
참조 배열을 할당해 바이트 계산도 확인했다. GEMQ GPU 커널 검증은 아니다.
상세 기록: cpu_verification.json

정확한 합산이라는 표현은 저장한 전문가 출력·gate의 FP64 평가를 뜻한다.
실제 BF16 블록 누적과 비트 단위로 같은 연산이라는 뜻은 아니다.
따라서 실제 검사에서 A/B가 고른 두 배분의 원래 BF16 블록 출력도 별도로 확인한다.

5. 계속할 조건과 종료 범위

A/B: 보정에서 고른 배분을 그대로 보류 입력에 적용한다. 평균 오차 감소 5% 이상,
문서 단위 대응 bootstrap 95% 구간의 하한이 0보다 크고, 실제 BF16 블록 평가에서도
사전 수치 동점 범위를 넘는 오차 감소가 있을 때만 다음 품질 검토로 간다. 5%는 자원 투자의 탐색 기준이며
지각 품질·perplexity의 의미 있는 차이라고 주장하지 않는다. 동점·동일 배분이나
기준 미달이면 이 작은 검사의 품질 방향은 종료한다. 다른 층을 추가해 구제하지 않는다.

B/C: 같은 점수와 선택을 전제로 비용을 비교한다. 모델 준비·양자화·출력 수집·
전송·캐시/교차항 생성·평가를 포함한 일회 총비용과 평가 구간 비용을 함께 낸다.
워밍업 후 B-C, C-B, B-C 순서로 3쌍을 측정한다. 총시간 중앙값 10% 이상 절감과
세 쌍 모두 같은 방향, 또는 최대 프로세스 메모리 20% 이상 절감과 시간 증가 5%
이하·GPU 최대 메모리 비증가를 탐색 기준으로 정했다. 조회 시간만으로 가속을 주장하지 않는다.
이는 아직 측정하지 않은 기준이며, CPU 정확성 검사 시간을 성능 결과로 쓰지 않는다.

실제 실행 상한은 준비·다운로드·검증·재시도를 포함해 120분, GPU allocated peak
20 GiB, 프로세스 RSS 48 GiB, 추가 디스크 20 GiB로 제한했다. 시계는 아직 시작하지 않았다.
자원 한도에 걸리면 미완료로 보고하며 품질 가설 실패로 처리하지 않는다.
두 방향이 모두 기준에 못 미치면 여기서 종료하고, 통과할 때만 전체 모델 평가와
기존 강한 방법 비교를 검토한다. 현재 단계에서 새 논문 주제로 채택한 것은 아니다.

남은 실행 준비는 모델 입력 캡처와 실제 가중치 왕복 검사다. 현재 설치된 Torch는
2.6.0이고 HQQ/GemLite가 없어 GEMQ 전체 코드를 바로 실행할 수 없다. 그러나 이번
RTN 목적함수 진단에는 해당 전체 스택이 필수는 아니다. 기존 환경을 바꾸지 않고
작은 참조 경로를 준비하며, 실제 GEMQ 커널 실행은 별도 검증 항목으로 남긴다.

고정 명세: registration.json
원문·코드 확인 범위: source_audit.json
모델/데이터 revision과 환경: environment_and_model.json
현재 결론: 기준선 확정과 CPU 검증 완료. 실제 MoE에서 교차항을 무시한 배분이
나쁘다는 증거와 C의 비용 이득은 모두 미측정이다.

실제 측정 전 추가 승인 사항:
24개 문서 모두 양자화를 끈 전체 캡처·재조립 경로와 원래 MoE 블록 출력을
형상·dtype·원소 비트 단위로 비교한다. 원래 계산 순서를 유지하고 허용 오차는 0이다.
native BF16의 오차 감소는 1e-10 + 1e-9*max(|L_A|,|L_B|)보다 커야 한다.
B/C의 각 측정은 독립 프로세스에서 수행하며 RSS의 과거 최고값을 공유하지 않는다.
전문가 4개는 공동 선택이 잘 관측되는 부분집합임을 명시하고 보류 입력의
전문가별·쌍별 공동 선택 횟수와 둘 이상 선택된 토큰 수를 보고한다.
