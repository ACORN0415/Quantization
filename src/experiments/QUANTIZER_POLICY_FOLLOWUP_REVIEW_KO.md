# 양자화기 × 저장 정책 비교 이후의 후속 검토

작성: 2026-10-29 (Asia/Seoul)

**상태: 검토 권고·미등록·미실행.** 이 문서는 실행 계획의 봉인이나 실행 허가를 대신하지 않는다.
기존 개발 비교의 표본·구현·진행 기준을 바꾸지 않으며, 새 보류 데이터를 사용하지 않았다.

**후속 상태 갱신:** legacy 개발 8/8개가 고정 기준 **NO-GO**로 종료됐다.
따라서 아래의 조건부 grouped 개발과 40개 보류 확인 권고는 **미채택·미실행**이다.
새 grouped GPU 개발 계획을 작성·등록하거나 실행하지 않았으며, 현 계획은 종료한다.
아래 내용은 NO-GO 이전의 조건부 검토 기록으로 남긴다.

## 1. 현재 개발의 판단을 먼저 마친다

[현재 개발 계획](QUANTIZER_POLICY_CROSS_DEVELOPMENT.md)은 이미 사용한 p0/p4, seed101의
RTN/KIVI-style × rolling/C-repeat 8개 생성이다. 각 프롬프트의 상호작용은

    I = (KIVI_C-repeat − RTN_C-repeat) − (KIVI_L − RTN_L)

이다. 기존 고정 기준은 두 프롬프트에서 I의 부호가 같고 각각 |I|≥1.0 MUSIQ이며,
모든 구현·재현·수치·비용 게이트를 통과하는 것이다. 이 기준을 결과에 맞춰 바꾸지 않는다.

- **NO-GO:** 현재 계획을 종료하고 결과를 정리한다. 양자화기·INT2·추가 표본으로 교체해
  같은 개발 GO를 구제하지 않는다.
- **GO:** 현재 두 수치 양자화 함수의 정책 의존성이 추가 검토할 만큼 있다는 판단이다.
  새 보류 생성이나 원본 KIVI 전체 방법의 우위·순위에 대한 판단이 아니다.
- 구현 실패·비유한 값·자원 초과는 가설의 NO-GO와 구분한다. 원인과 중단 상태를 기록한다.

## 2. GO여도 현재 KIVI-style 그대로 보류를 크게 늘리지는 않는다

현재 [독립 재구현](../kvq/quant.py)은 `[B, groups, g, H, D]`에서 value의 H×D를 함께
줄여 토큰당 scale/offset 각각 하나를 만든다. 공식 KIVI의 `quant_and_pack_vcache`는
각 head 내부의 D축을 group_size로 나눈다. H=12, D=128, gV=16이면 토큰당
scale/offset은 각각 12×8=96개다. 현재 구현과는 수치 오차뿐 아니라 메타데이터 수가 다르다.

공식 추론에는 BF16 residual의 수명과 과거 packed code의 보존도 들어 있다.
현재 L/C-repeat의 반복 encode 일정은 원본 lifecycle의 재현이 아니다.
따라서 현재 결과가 GO여도 다음처럼 표현해야 한다.

> 현재 재구현의 두 수치 양자화 함수에서, 고정한 저장 일정에 따라 상대 품질 차이가 달라졌다.

이를 “기존 KIVI의 평가 순위가 저장 정책 때문에 바뀐다”로 확대하지 않는다.

### 확인한 공식 자료의 범위

- [KIVI 논문](https://proceedings.mlr.press/v235/liu24bz.html)
- [공식 수치·패킹 구현의 main URL](https://raw.githubusercontent.com/jy-yuan/KIVI/main/quant/new_pack.py):
  `quant_and_pack_kcache`, `quant_and_pack_vcache`의 그룹 축과 min/max 계산 확인.
- [공식 모델 구현의 main URL](https://raw.githubusercontent.com/jy-yuan/KIVI/main/models/llama_kivi.py):
  `residual_length`, full-precision residual, 과거 packed state 연결·보존 확인.

이번 검토는 **위 main URL의 본문 확인**이다. 여기서 immutable commit SHA를 확인했다고
주장하지 않는다. source pin은 별도 구현 후보 검토 담당이 확인 중이며, 구현 검증 계획을
등록할 때 commit·파일 SHA와 판본을 확정해야 한다. 공식 코드를 실행해 수치 재현한 것도 아니다.

## 3. GO 다음은 공식 그룹 정의를 반영한 별도 개발 검증

기존 수치 파일을 고치지 않고 별도 구현·별도 계획·별도 source hash로 진행할 후보이다.
원래 개발의 GO를 사후 재정의하거나 NO-GO를 덮어쓰는 단계가 아니다.

### 바꾸는 것: 수치 양자화기의 그룹 정의

- key: 토큰 축 그룹별로 channel마다 min/max를 계산한다.
- value: 토큰별·head별로 D축을 나눈 그룹마다 min/max를 계산한다.
- key_group=16과 value_group=16을 별도 인자로 명시한다.
- constant/zero 그룹의 안정화, BF16 입력 산술, FP16 scale/min 저장과 복원 반올림을 명시한다.
- 공식 코드와 비퇴화 입력의 codes·scales·min·복원을 대조한다. dtype와 안정화 차이가 있으면
  공식 구현과의 비트 일치 범위를 구분한다.
- value metadata 증가와 패딩을 반영해 유효/패딩 코드·scale·offset·BF16 버퍼를 다시 센다.
  이름만 KIVI로 고치거나 같은 바이트라고 가정하지 않는다.

### 유지하는 것: 공통 저장 일정

- 현재 청크는 두 정책 모두 BF16으로 읽는다.
- L/C-repeat의 호출·쓰기·eviction 일정은 그대로 유지한다.
- 원본 KIVI residual/immutable lifecycle은 이 단계에 추가하지 않는다.
- 이 비교의 이름은 **“KIVI-compatible 수치 양자화기를 공통 저장 일정에 넣은 비교”**다.
  원본 KIVI 시스템 전체의 성능 평가라고 부르지 않는다.

정렬 디버그를 위해 key_group=24를 쓰더라도 value_group은 16 등 D를 나누는 값으로 유지한다.
D=128은 24로 나누어떨어지지 않으므로 이전의 단일 g=24 설정을 모든 축에 복제하면 안 된다.

### 최소 개발량과 새 진행 기준

두 기존 개발 프롬프트에서 새 KIVI-compatible × L/C-repeat의 **4개 생성**을 우선 후보로 둔다.
RTN 셀은 기존 동결 결과를 기준으로 사용할 수 있으나, 최소 한 실제 RTN 출력 parity 게이트와
소스·환경 대응 검사를 권한다. 현재 처리량을 이용한 거친 비용은 **약 15–20분**이며,
구현·게이트 비용과 새 quantizer의 실측 시간은 별도다. 완료 시간 보증이 아니다.

수정된 결과를 보기 전에 이 단계의 효과·자원·중지 기준을 새로 고정한다.
현재 legacy 결과와의 방향 유지까지 요구할지, 수정된 정의의 양측 상호작용을 새 탐색으로
볼지도 명시한다. 방향이 바뀌면 원래 패턴의 재현이라고 부르지 않는다.

상호작용이 사라지면 현재 결과가 legacy value 그룹 정의에 민감한 현상일 가능성을 먼저
정리한다. 이를 실패가 아닌 듯 포장하거나, 좋은 결과가 나오는 정의를 계속 골라 같은
확증 주장으로 이어가지 않는다.

## 4. 유지될 때의 최소 보류 확인 후보

아래는 실행 승인이 아닌 표본·분석 후보다. 구현 게이트와 시간 실측 후 최종 계획을 봉인한다.
새 입력을 생성·사용하기 전에 프로토콜·표본·분석 코드·소스·가중치 해시를 확정한다.

| 항목 | 최소 후보 |
|---|---|
| 표본 | 기존 개발·파일럿·본 실험과 겹치지 않는 새 프롬프트 8개 |
| 시드 | 실행 전 고정한 새 시드 1개를 모든 팔에 공통 사용 |
| 비교 팔 | RTN/KIVI-compatible × L/C-repeat, 총 32개 |
| BF16 | 프롬프트당 1개, 총 8개 권고 |
| 총량 | BF16 포함 **40개 생성 궤적** |
| 주지표 | 원본 float 디코딩 후반 프레임 249–500의 252개 MUSIQ 평균 |
| 주 대비 | 각 프롬프트의 I, 그리고 그 8개 평균 |
| 검정 | n=8의 양측 정확 부호 반전 검정, alpha=.05 하나 |
| 신뢰구간 | 사전 고정 seed·반복 수의 95% 프롬프트 부트스트랩 |
| 보조 | 각 정책의 KIVI−RTN, 경계−내부, DINO·flow·coverage, 실제 바이트 |
| 중지 | 소스 불일치·비유한 주 상태·게이트 실패·자원 초과 등 실행 실패만. 중간 p값으로 중지하지 않음 |

현재 처리량을 이용한 비용은 대략 **2–2.5시간**이나, 최종 추정은 수정 quantizer의 실측에
따라 계획 봉인 전에 다시 계산한다. 시드 2개라면 비교 64개와 BF16 16개로 총 80개가 되어
최소 확인 범위를 벗어난다. 한 시드의 최소안은 그 시드에 조건부인 확인이라는 한계를 남긴다.

n=8의 정확 검정에서 최소 양측 p는 0.0078125다. 짝지은 상호작용의 대칭성·교환 가능성
가정을 명시하고, 작은 편의 표본의 부트스트랩 구간이 근사적임을 밝힌다. 개발 n=2에서
추정한 변동으로 정밀한 검정력을 주장하지 않는다. 음성 결과를 동등성으로 바꾸지 않는다.
프레임이나 청크를 독립 표본으로 세지 않고 전체 프롬프트별 I도 공개한다.

## 5. 원본 residual/immutable lifecycle은 별도 시스템 질문이다

공식 residual과 단회 packed 저장을 동시에 도입하면 수치 양자화기와 저장 일정이 다시 묶인다.
이를 위 공통 일정 2×2 주 비교에 조용히 섞지 않는다.

기존 방법의 실제 배포 선택이 달라지는지 주장하려면 별도의 native-adaptation 팔이 필요하다.
영상에서는 같은 현재 청크의 K/V를 denoise마다 덮어쓰므로 LLM의 token-append lifecycle을
그대로 적용할 수 없다. 다음 세 상태를 따로 정의해야 한다.

1. key의 그룹 완성 대기 tail과 flush 시점.
2. value의 최근 BF16 residual과 FIFO 수명.
3. 현재 4,680토큰 청크를 덮어쓰며 유지하는 BF16 pending.

key tail과 현재 청크 pending은 같은 버퍼가 아니다. 같은 메모리 예산 비교에는 각 버퍼와
scale·min·코드·인덱스를 포함한다. 실제 패킹·복원·attention 비용도 그 구현에서 함께 잰다.

## 6. 기대할 수 있는 기여와 아직 없는 기여

이 순서로 성공하면 수치 양자화기 선택과 저장 정책이 상호작용한다는 근거가 강해진다.
그러나 한 영상 모델·한 비트폭·한 시드의 내부 구현 비교만으로 기존 방법 전반의 순위가
잘못됐다고 결론 내리거나 저널 신규성을 보증하지 않는다.

원본 KIVI 전체 방법의 순위 재평가에는 충실한 lifecycle 적응이, 실용적인 효율 주장에는 실제
패킹과 같은 메모리 예산 비교가, 일반성에는 다른 모델·양자화기의 검증이 추가로 필요하다.
그 투자는 위 작은 개발과 보류 확인이 끝난 뒤 결정하는 것이 적절하다.

**권고 순서:** 현재 개발의 고정 판단 → GO일 때 공식 그룹 정의의 별도 작은 개발 → 유지될 때
40개 보류 확인 → 그 결과에 따라 native lifecycle·패킹·다른 모델의 투자 여부 결정.
