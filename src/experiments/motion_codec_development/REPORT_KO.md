# 움직임 정렬 KV 압축 1차 개발 진단 — 제한된 전역 이동 NO-GO

2026-10-29 22:38 KST 완료. [측정 전 v2 계획](../MOTION_CODEC_DEVELOPMENT.md)의 첫 단계만 실행했다. **K 예측 MSE로 선택한 전역 정수 이동은 두 개발 입력 모두 추가 이득이 없었다.** 공유 이동과 층별 이동이 모두 `(dy,dx)=(0,0)`을 골랐고, 사전에 정한 두 대비 5% 개선 기준을 통과하지 못했다. 새 보류 영상 생성·조밀한 지도 개발로 자동 확대하지 않는다.

## 무엇을 검사했는가

기존 개발 프롬프트 p0/p4, seed101의 BF16 첫 8청크를 다시 실행했다. 층 `{0,14,29}`, 청크 `{0,1,6,7}`의 최종 context refresh에서 실제 pre-RoPE K와 V를 캡처했다. 각 청크 안의 프레임 `0→1`, `1→2`를 독립 참조쌍으로 삼았다. 참조는 직접 INT4 양자화 후 복원한 값이며, BF16 원본을 예측 참조로 사용하지 않았다. 각 쌍의 의존성은 길이 1이고, 앞 잔차의 복원을 다음 쌍에 잇지 않는다.

직접 양자화, 동일 위치 잔차, 층0 K로 고른 공유 이동 잔차, 경계 처리를 맞춘 동일 위치 잔차, 층별 이동 잔차를 비교했다. 이동 후보는 토큰 좌표 ±2의 25개 전역 평행이동이다. 공유·층별 선택은 **현재 K의 양자화 전 예측 MSE**를 최소화한다. V·잔차 양자화 후 손상·attention 출력·미래 query를 최적화한 것이 아니다. 층별 선택도 전체 대응·코드의 최적 상한이 아니다.

K4V4, g16, FP32 양자화 계산·FP16 scale·uint8 코드 컨테이너를 사용했다. 과거 BF16 RTN 경로와 수치 구현이 같지 않다. 동일 위치 잔차는 TempoKV의 학습된 시간 예측기와 K→V 예측을 재현한 것이 아니다.

## 결과

각 값은 K/V 상대 L2를 평균하고, 3층·4청크·2프레임 쌍을 동일 가중한 값이다. 입력당 팔별 24셀, 전체 240행이며 독립 표본은 개발 프롬프트 2개다. p값은 계산하지 않았다.

| 입력 | 직접 양자화 | 동일 위치 잔차 | 공유 이동 잔차 | 경계 일치 동일 위치 | 층별 이동 잔차 | 공유 이동 추가 개선 |
|---|---:|---:|---:|---:|---:|---:|
| p0 | 0.06494230 | 0.04701801 | 0.04701801 | 0.04701801 | 0.04701801 | 0% |
| p4 | 0.06059883 | 0.04734214 | 0.04734214 | 0.04734214 | 0.04734214 | 0% |

공유 이동의 독립 선택 16개와 층별 선택 48개가 모두 zero shift다. 따라서 경계 대조군도 같은 예측값을 사용한다. **검사한 선택 규칙이 zero shift를 선호했다**는 결과다. 모든 nonzero 이동이 잔차 부호화 오차나 attention 오차에서도 무조건 나쁘다는 증명은 아니다.

동일 위치 잔차의 직접 양자화 대비 오차 감소는 p0 27.60%, p4 21.88%다. 이것은 고정 비트폭에서의 복원 오차 결과다. 실제 비트레이트를 줄였거나 생성 품질이 좋아졌다는 뜻은 아니며, 기존 예측 잔차 압축을 넘어서는 신규성 근거도 아니다.

입력·층·쌍 전체 평균을 성분별로 보면 다음과 같다.

| 팔 | K pre-RoPE 상대 L2 | K 원래 위치 RoPE 후 상대 L2 | V 상대 L2 |
|---|---:|---:|---:|
| 직접 | 0.04811740 | 0.04817200 | 0.07742373 |
| 동일 위치·공유 이동·층별 이동 | 0.02564572 | 0.02574893 | 0.06871444 |

RoPE 후 오차도 기록했지만 실제 attention 읽기·출력 오차는 측정하지 않았다. 새 생성 경로에 codec을 연결하거나 MUSIQ를 평가하지 않았다.

## 바이트와 실행 비용

다음은 **한 층에서 K/V 참조 한 프레임과 대상 한 프레임을 함께 저장하는 텐서 payload**다. 여러 쌍을 동시에 보관하는 캐시의 총량으로 읽으면 안 된다. anchor code·scale·padding을 포함한다.

| 팔 | 실제 uint8 컨테이너 payload | 가상 INT4 packed 추정 |
|---|---:|---:|
| 직접 | 10,838,016 B | 6,021,120 B |
| 동일 위치·공유 이동·층별 이동 잔차 | 10,838,024 B | 6,021,128 B |
| 경계 일치 동일 위치 | 10,838,032 B | 6,021,136 B |

이동 헤더는 K/V마다 int16 dy/dx 4바이트씩 실제 중복 계상했다. 경계 대조군은 zero-shift 헤더에 마스크 기하 4바이트씩을 추가했다. 참조쌍 ID·형상·비트폭은 고정 프로토콜/파일 헤더로 해석하며, 범용 직렬화 포맷은 구현하지 않았다. 이미 복원한 참조의 임시 BF16 텐서는 `reference_restore_workspace_bytes`에 별도로 기록했다. 배포 시 최종 전체 캐시의 참조 pinning·eviction·복원 peak는 아직 검사하지 않았다. 가상 packed 열을 실제 GPU 상주량으로 부르지 않는다.

- 캡처는 프롬프트당 모델 로딩·텍스트 인코딩·계측 포함 약 59초였고, 별도 분석 루프는 1.49초였다. 프로세스 시작/import 비용은 이 합계 밖이다.
- 캡처 프로세스의 peak allocated는 각각 8.673 GiB, peak reserved는 9.039 GiB, CPU lifetime high-water는 약 33.175 GiB였다. 이는 모델·BF16 기준 버퍼·무손실 게이트·캡처를 포함한 진단 실행 자원이며 codec 배포 메모리가 아니다.
- 분석 프로세스 peak allocated 0.227 GiB, reserved 0.303 GiB. 로컬 캡처 24개는 합계 0.666 GiB이며 재검토를 위해 보관한다.
- 대응 검색 시간과 encode+decode+지표 계산 묶음 시간은 CSV에 있다. 워밍업·반복이 없고 anchor encode/참조 restore도 묶음 밖이므로 처리량·실제 추론 지연의 근거로 사용하지 않는다. RoPE 오차 평가와 검증 동기화도 포함된다.

## 게이트·재검토와 중단 범위

CPU 검사 8개가 통과했다. 관찰 hook을 단 BF16 출력은 프롬프트당 8/8청크에서 기존 기준과 비트 단위로 같았다. 실제 pre-RoPE K의 무손실 잔차 복원 후 원래 위치 RoPE 재적용 게이트도 캡처당 12건씩 통과했다. 소스 해시는 캡처/분석 전후 일치했고 24개 캡처 SHA256을 보존했다.

첫 계획 커밋은 `02bb705`, 실제 캡처 전 경계 대조군 보강은 `5fe171a`다. 합성 난수 모의 검토가 발견한 경계 혼합 요인을 먼저 수정했다. 실제 프롬프트 K/V를 저장하기 전 모델 로딩 중 초기 실행을 중단했으며, 첫 작업 경로 오류도 캡처 전에 수정했다. 경위는 v2 계획과 로컬 startup 로그에 남겼다.

별도 에이전트와 루트의 읽기 전용 재계산은 240행의 완전성·평균·판단·바이트·24개 해시를 확인했다. 같은 작성 주체의 검토이며 외부 독립 검증은 아니다. 감사 도구는 게이트 manifest를 확인하며 전체 모델을 다시 실행하지 않는다.

```bash
cd ~/Quantization
/usr/bin/python3 tools/audit_motion_codec_probe.py
bash tools/watch_progress.sh 0
```

이번 **제한된 전역 이동 변형**은 여기서 종료한다. 객체별/부분영역 대응, sub-token 이동, 가려짐을 다루는 조밀한 지도 전체를 기각하지 않는다. 그러나 현재 결과가 그 복잡한 구현에 추가 투자할 양의 근거를 제공하지도 않는다. 새 가설을 열려면 이번 NO-GO와 분리해 필요성·대조·진행 기준을 새로 정해야 한다. solver 공유 코드 후보 역시 AccuQuant 등과의 목적함수 중복 문제가 남아 있어 자동 후속 실험으로 전환하지 않는다.
