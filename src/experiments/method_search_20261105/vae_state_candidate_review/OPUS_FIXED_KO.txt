 구조(vae.py 369–425, _video_vae dim=96, dim_mult [1,2,4,4]): decoder dims [384,384,384,192,96], 해상도 60×104 → 120×208 → 240×416 → 480×832.
 CausalConv3d(14–36)는 temporal kernel 3 conv마다 입력의 마지막 CACHE_T=2 프레임을 보관한다. 대략:
  middle 384ch@60×104 4개 ≈38MB, stage0 6+resample ≈67MB, stage1 192/384ch@120×208 ≈250MB, stage2 192ch@240×416 6개 ≈460MB,
  stage3 96ch@480×832 6개+head ≈1.07GB → feature state 합 ≈1.9GB(BF16), INT8로 바꾸면 ≈0.95GB 절감(scale 메타 제외). 1×1 shortcut은 캐시 없음.
 비교 대상(정적): 출력 누적 torch.cat(vae.py 559–566)은 최종 501×3×480×832 BF16 ≈1.2GB이고 cat마다 새 버퍼라 순간 ≈2.4GB; wrapper 107 .float()로
  FP32 사본 ≈2.4GB 추가. 프레임당 full-res 활성(96ch×4프레임) 수백 MB 단위 workspace.
 → state는 peak의 한 성분일 뿐이고, 출력 누적/FP32 승격만 없애도(스트리밍) 비슷하거나 더 큰 절감이 정확성 손실 없이 가능하다. 시간 측면에서도 cat/state 복사는

3. 1차문헌(helper 확인, 세 링크 모두 제목 일치·접근 가능)
 - LightVAE 2610.14726: low-rank·block pruning·feature alignment, Wan VAE family 처리량 가속. state 양자화 없음(초록 기준, 본문 미확인).

4. 가장 강한 단순 해법
 메모리가 문제라면: (i) 출력 프레임을 생성 즉시 CPU/파일로 스트리밍(누적 cat·전체 .float() 제거), (ii) 기존 공간 tiling, (iii) 정확 Conv3D lowering —
 모두 수치 동일 또는 근접을 유지한다. 그래도 state가 병목으로 측정될 때만 plain INT8 RTN state가 단순 기준선이다.
