VAE 정밀도 2팔 진단 — 실행 전 독립 설계 및 코드 준비

판단
기존 BF16 VAE가 공식 경로와 같다는 사실을 버그로 해석하지 않습니다. 그래도 동일하게 저장된 latent 하나를 fresh checkpoint의 BF16/FP32 두 VAE로 복원하면, generator를 고정했을 때 VAE 실행 정밀도 묶음이 RGB에 미치는 수치적 영향은 직접 비교할 수 있습니다. 이 좁은 질문에는 2회 복원의 실행 가치가 있습니다. FP32가 원래 의도한 영상의 정답이거나 품질이 낫다는 검사는 아닙니다. 새 양자화 방법, 끝난 paired/full-H 후보의 구제, 긴 문맥 유용성 검사가 아닙니다.

등록할 입력과 연산
- 단일 기존 입력: /home/acorn0415/sfq_data/mechanism/fr/p00_s303_BF16/latent.pt. sampling.json의 latent_file_sha256=b7a553d50254e290707fb32a31c05233667d57d85ccc140eca7273e1762367cf를 최종 root LOCK와 대조해야 합니다. 준비에서는 stat/JSON만 읽었고 latent는 열지 않았습니다.
- checkpoint: src/wan_models/Wan2.1-T2V-1.3B/Wan2.1_VAE.pth. 과거 full_obq_rollout_pilot/LOCK.json이 기록한 파일 SHA256=38071ab59bd94681c686fa51d75a1968f64e470262043be31f7a094e442fd981. 준비에서는 파일 stat/기존 LOCK만 읽었습니다. 실제 파일 및 저장 weight dtype는 미검증이며 실행 시 각 fresh load 이전 및 마지막에 파일 hash를 확인합니다. 원 checkpoint의 floating parameter가 FP32인지 검사하고 아니면 무효 처리합니다. BF16로 반올림한 모델을 float()로 올려 FP32 원가중치라고 부르지 않습니다.
- 순서 고정: BF16 fresh load → BF16 복원 → 모델/GPU 출력/입력 정리 → FP32 fresh load → FP32 복원. 동일 latent 원소 값을 BF16 또는 FP32로 변환하고 CPU 원값과 동등성을 확인합니다. 원입력 BF16, shape[1,126,16,60,104] 계약 불일치면 중단합니다.
- src/utils/wan_wrapper.py의 WanVAEWrapper 클래스 AST를 변경 없이 실행하며, _video_vae 바인딩은 src/wan/modules/vae.py 전체 원모듈을 importlib로 직접 읽습니다. 이 방법은 text encoder/generator를 생성하지 않기 위한 import 격리이며 decode 함수 본문을 복제하거나 수정하지 않습니다. 전체 두 source hash 및 사용한 클래스 AST hash를 기록합니다.
- use_cache=False를 유지합니다. native decode는 호출 처음/끝에 clear_cache하고 내부 latent126회 decoder 호출 사이 temporal feature cache를 이어갑니다. 시간축 분할 방식이나 decoder 내부 torch.cat을 변경하지 않습니다.
- mean/std는 wrapper의 CPU FP32 속성에서 latent dtype으로 변환하고 reciprocal도 해당 dtype으로 계산하는 원규칙 그대로입니다. 따라서 비교에는 가중치 반올림, 연산 정밀도, 정규화 반올림, dtype별 backend 선택이 모두 포함됩니다. 이들을 개별 원인으로 분리하는 검사는 아닙니다.
- TF32 matmul/cuDNN off, CUDA/CPU autocast off, cuDNN benchmark off, deterministic True를 두 팔에 동일 적용합니다. native VAE SDPA가 dtype에 따라 다른 backend를 선택할 가능성은 그대로 남고 해당 묶음의 효과로만 해석합니다. 과거 실행과의 bit identity를 주장하지 않습니다.
- wrapper의 FP32[-1,1] clamp 결과를 CPU로 옮긴 뒤 FP32 ×0.5+0.5, clamp[0,1]을 적용합니다. 같은 FP32 변환식이며 CPU/GPU 위치 차이의 전원소 동등성은 실행 전 미검증입니다. 비교 대상 두 팔 모두 동일 CPU 변환을 사용합니다. MP4 디코드/압축결과를 참조하지 않습니다.

산출물과 판정
- 두 팔 전체501 RGB를 CPU FP32 메모리에만 유지합니다. 모든501프레임에서 차이의 MSE, MAE, 절대차 q99(전체 원소의 linear quantile), 각 팔 mean RGB를 FP64 CPU 계산합니다. 공간/시간 표본을 뽑아 전체 통계라고 부르지 않습니다.
- 고정8프레임 0,80,160,240,320,400,480,500만 FP32 tensor와 PNG로 저장합니다. PNG는 FP32[0,1]×255의 uint8 변환이며 수치 비교는 PNG 이전에 합니다. 전체 RGB/새 MP4/새 generator 결과는 저장하지 않습니다.
- 주 선택 규칙 제안: frame249..500(252개)의 RGB 원소 MSE 평균의 제곱근이 0.02 이상이면 '평가 정밀도의 영향 추가 검토', 그 외는 '현재 정밀도 개입 확대 중지'입니다. 이는 [0,1] RGB에서 약5.1/255 크기의 사전 자원배분 기준일 뿐 통계적 유의성/영상 품질/인과적 결함 임계값이 아닙니다. 두 방법의 순위나 새로운 방법 성공으로 쓰지 않습니다.
- root의 초안에 있던 'early-late meanRGB 변화 50% 감소'를 AND 조건에서 제거할 것을 권고합니다. 작은 mean 변화는 정적인 출력·노출·구도 변화에도 생기며 낮을수록 좋다는 근거가 없습니다. FP32가 실제 장면 변화를 되살리면 변화량이 커질 수도 있습니다. 따라서 이 조건은 필요한 정밀도 민감성을 거짓 음성으로 막거나 품질 열화를 긍정할 수 있습니다. early0..125와 late375..500의 meanRGB 차 벡터/L2 및 감소율은 설명용으로만 보고합니다. BF16 변화량0이면 감소율은 정의하지 않습니다.
- 위 단일 규칙도 root/실제 Opus 통합 전 제안입니다. worker LOCK에는 정확한 decision_rule 문자열이 필요하며 다른 규칙으로 조용히 실행하지 못합니다. 수정이 필요하면 실자료 접근 전에 별도 source/검사 기록을 남겨야 합니다.
- FP32 변화가 커도 품질 향상/정체성 보존을 입증하지 않습니다. 작아도 모든 VAE/latent 원인 배제는 아닙니다. 이 입력은 이미 여러 번 본 개발 자료이며 독립 보류/모집단 추론 대상이 아닙니다.

자원과 실패
GPU를 쓰는 프로세스1개, VAE 복원 정확히2회, generator0. root LOCK 확인부터 source hash/import/모델/latent load/복원/선정프레임 저장/통계/사후hash까지600초. CPU4, 프로세스 RSS12GiB, PyTorch GPU allocator22GiB, 준비 폴더 합계256MiB. 임계값/시간 초과, OOM, 비유한 값, 입력/출처/shape/dtype 불일치는 모두 판단 불가이며 재실행·FP16 팔·streaming 우회·분할 decode로 범위를 바꾸지 않습니다.

단일 출력은 FP32 2,400,952,320B(2.236GiB), CPU 두 팔 유지 약4.472GiB입니다. native cat/float/stack 동안 GPU 출력 자체가 중복되므로 GPU 출력 버퍼만 약4.472GiB 하한이며 모델·feature cache·FP32 upsample·conv/SDPA workspace가 추가됩니다. 코드만으로22GiB/12GiB 통과를 보장하지 않습니다. 선택 FP32 두 팔 저장 payload는76,677,120B이며 PNG·메타데이터가 추가됩니다.

worker는 root 승인 LOCK가 없으면 RUN도 만들지 않고 거부합니다. 승인 후에는 exclusive RUN으로1시도만 허용하고 0.1초 watchdog이 시간/RSS/disk/GPU allocation peak를 감시합니다. 초과 시 실패 기록 후 해당 단일 프로세스를 종료합니다. CUDA allocator fraction22GiB도 설정합니다. CPU 순간 peak는 종료 전 ru_maxrss로 다시 검사합니다. 감시 주기보다 짧은 실제 초과를 예방한다고 주장하지 않으며 사후 위반이면 무효입니다. SIGTERM/SIGINT는 예외 실패로 기록하고 재실행하지 않습니다. worker가 자식 GPU 프로세스를 만들지 않습니다. 외부 root 감독/단일 GPU 소유 조건은 별도로 유지해야 합니다.

준비 검증과 남은 항목
SELFTEST_V2.json의17건은 작은 CPU 합성 통계, shape/dtype 거부, 잘못된/누락 LOCK, source AST/컴파일 검증입니다. 실제 VAE/latent/checkpoint load, CUDA 호출, 501프레임 native decode, watchdog의 live GPU 동작을 검증한 것이 아닙니다. native helper는 source 두 파일의 dtype/출력 수명 계약을 독립 읽기 확인했고 모델/텐서/GPU0입니다. 현재 READY는 구현 검토용 준비 완료이며 실제 Opus 검토나 root GPU 실행 승인을 뜻하지 않습니다. 준비 절대마감17:23UTC를 유지합니다.

실행 전 root 검토 보완: atomic rename 중 사라지는 .tmp 파일만 disk 집계에서 제외합니다. 다른 watchdog 오류는 명시적 실패 기록과 프로세스 종료로 처리하고, 정상 완료 전에 watcher 생존·오류 없음·정상 종료를 확인합니다. 이전 source/READY/SELFTEST는 PRE_ROOT_ROBUSTNESS_FIX 및 기존 원기록으로 보존했습니다. 이 수정은 수치식/입력/팔/기준을 바꾸지 않습니다.
