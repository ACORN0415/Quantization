3. run_guarded_once.py (dc671f67) 소스 검토
충족(소스 기준)
- --execute가 없으면 출력만 하고 실행하지 않는다.
- 원 RUN을 확인한다: sha 6d667837, status invalid, started 1793886840.4246237, stage 체인, started+2700=절대마감. 원 LOCK과 driver sha도 ORIGINAL_RUN_BINDING으로 확인한다.
- HERE에 RUN.json이나 ONCE_CLAIM이 있으면 거부한다.
- LOCK 필드를 요구한다: root/Opus/validity true, validity_repair_additional_run_authorized=true, maximum_additional_runs=1, original_run_sha256, absolute_deadline_utc, pending 없음.
- driver.verify_lock(SOURCES_V5 전체 hash 포함)을 하고, wrapper 자신의 hash가 LOCK sources에 있는지 확인한다.
- ONCE_CLAIM은 open('x')로 배타 생성하며, 검증을 마친 뒤에 생성한다. 따라서 검증 실패는 claim을 소모하지 않는다.
- supervisor는 1회만 Popen한다. 재시도 루프가 없고, 실패하면 RuntimeError("no further retry").
- 마감
  - 시작 시 남은 시간 = 절대 UTC 마감 − now. 이것으로 monotonic 마감을 만든다.
  - 루프와 완료 후 최종 검증에서 UTC와 monotonic 둘 다 검사한다.
  - 원 시작 기준 2700초를 공유하며 새 45분을 주지 않는다.
  - driver 내부 Budget은 자체 2700초를 갖지만 wrapper가 더 엄격하게 상한을 강제한다.
- 자원
  - 원 stage0과 V5 폴더의 합계 디스크 ≤2GiB를 시작 전, 루프 중, 완료 후에 검사한다. 현재 약 11.7MB+0.17MB.
  - 자식·후손의 RSS ≤8GiB(0.25초 간격), wrapper RSS도 검사한다.
  - CUDA_VISIBLE_DEVICES='', OMP/MKL 4.
- 정리: kill_owned는 이 실행에서 관측한 (pid, create_time) 쌍만 terminate하고, 2초 뒤 같은 쌍만 kill한다. 다른 process는 건드리지 않는다.
- 완료 후 validate_original과 verify_lock을 다시 해서 원 기록이 그대로임을 확인한다.

결함·한계
[S1, 수정 권고 — interrupt 경로] 정리는 except Exception에서만 일어난다.
  - KeyboardInterrupt(BaseException)나 SIGTERM이 오면 kill_owned가 호출되지 않는다.
    - SIGTERM 핸들러가 없으므로 기본 동작으로 wrapper가 즉시 종료되고 finally도 실행되지 않는다.
  - supervisor는 start_new_session으로 분리돼 있으므로 wrapper가 interrupt되면 고아로 계속 돈다. 그때 남는 것은 자체 2700초 Budget뿐이어서 원 절대마감을 넘겨 RESULT를 쓸 수 있다.
  - 정상 경로에는 영향이 없다.
  - 최소 수정: except BaseException에서 정리하고, signal.SIGTERM 핸들러가 예외를 던지게 한다. 2줄 수준이다.
  - 수정하지 않는다면 조건 C1로 대체한다.
[S2, 경미 — 관측 간격 race] kill_owned는 0.25초 폴링에서 이미 관측한 후손만 정리한다.
  - 마지막 폴링 직후에 생성된 arm child는 정리 대상에서 빠질 수 있다.
  - supervisor가 SIGTERM으로 죽어도 그 child는 별도 session이라 계속 돈다.
  - 창이 0.25초 이하이고 child 수명은 초 단위라 확률은 낮다.
[S3, 경미 — 분류] OSError에 PermissionError와 FileExistsError가 포함된다.
  - 루프 안이나 완료 후 verify_lock에서 PermissionError가 나면 'incomplete_budget'으로 분류돼 'invalid'와 섞인다.
  - 해석상 둘 다 판정 불가라 영향은 작다.
[S4, 경미 — 원 산출물 binding 범위] validate_original은 원 RUN, LOCK, driver만 hash로 묶는다.
  - FAILURE_arm_18_R_bf16.json(fcfe7850), PREPARE_18.json, prepared/layer18.pt, log는 wrapper가 확인하지 않는다.
  - 새 LOCK의 review_evidence에 포함하거나 실행 전후 기록이 필요하다.
- V5는 새 HERE(…_packet_contract_fix)를 쓴다.
  - driver의 DataAccess는 HERE/prepared만 허용하고, save_tensor는 기존 파일이 있으면 거부한다. 따라서 원 prepared나 RUN을 재사용할 경로가 없다(소스 기준).
