같은 바이트 head 선택 CPU 진단 — 결과 보고 — 2026-11-05

판정: 시험한 개발 부분문제에서 고정 선택으로 충분하며, 청크별 norm 적응 선택을 새 방법으로 확장할 추가 이득은 확인되지 않았다.
등록한 frame primary의 '계속할 근거'는 거짓, '고정 규칙으로 충분' 조건은 참이다.
이 결론은 head에 높은 정밀도를 주는 행위가 무의미하다는 뜻이 아니다. 그 이득을 얻기 위해 입력마다 다시 선택할 필요가 없었다.

1. 실행 유효성과 자원
- 지정한 p0/p4, seed101, chunk7 첫 denoise, layer8/20/28/29의8개 캡처를 모두 완료했다.
- 캡처8개 SHA256/파일 크기가 원 manifest와 일치했고, 독립 감사에서 SHA256을 다시 확인했다.
- frame/chunk 각각 fixed_h00..h11와 norm 후보의 실제 CPU packed tensor payload가 전부 동일했다.
- frame 후보의 과거6청크 K+V payload:55,904,262바이트. no-upgrade는54,097,926바이트.
- chunk 후보의 동일 payload:55,805,958바이트. no-upgrade는54,005,766바이트.
- padding code, FP16 scale, 청크당 head index1바이트를 실제 tensor payload에 포함했다.
  Python 객체, 공통 형상정보, 공유 Hadamard 행렬, attention 작업공간은 제외다. 실제 GPU peak 절약을 의미하지 않는다.
- GPU0회, 실제 캡처의 quantize/attention은 CPU4스레드. 전체401.67초(6분41.67초), 최대RSS2,306,633,728바이트(약2.148GiB).
- 45분/RSS8GiB/신규디스크2GiB 상한 내 완료. 감사 시 작업 폴더96,192바이트였고 후속 보고서로 소량 증가했다.
- 코드와 등록의 hash는 실행 전 lock과 일치했고 실행 중 변경하지 않았다.

2. 등록한 주 판정(frame grouping)
동일 바이트에서 norm의 총 SSE는 반대 개발 프롬프트의 post-W_o SSE로 고른 fixed보다0.150838% 높았다.
p0은0.130846% 악화, p4는0.177916% 악화로 두 프롬프트 모두 추가 개선이 없었다.
8사례 중 개선1, 수치 동점5, 악화2이며, nonworse6/8은 충족했지만 총5% 개선 및 두 프롬프트 개선을 충족하지 못했다.
청크별 norm 선택이 한 head로 고정된 사례는6/8이다. '1% 개선 미달 + 6/8이상 고정 또는 악화' 종료 조건이 충족됐다.
노름 통계만으로 반대 프롬프트에서 정한 더 싼 고정표와 비교하면 norm의 총 SSE 개선은0.123805%로 작았다.

3. 결과가 의미하는 것
- 층28/29의 no-upgrade 대비85~96% 국소 오차 감소는 확인됐다. 그러나 고정head11/9가 norm과 정확히 같은 점수를 냈다.
- 동적 선택이 실제 바뀌는 layer20에서는 norm이 fixed head4보다 p0에서2.88%, p4에서9.42% 악화했다.
- p4/l8에서는 norm이 반대 prompt 점수 선택 fixed보다12.90% 좋았지만, 노름만으로 고른 반대 prompt 고정head10보다0.79% 나빴다.
  한 입력에서만 좋은 대조를 골라 선택기의 성과로 제시하지 않는다.
- 12개 fixed-head 균등 기대와 비교한 norm의 이득은 존재한다. 이것은 중요한 head를 보호하는 효과를 지지하지만,
  고정표보다 복잡한 적응 규칙의 추가 효과나 신규성을 입증하지 않는다.
- 상수 선택6사례는 규칙이 전체 입력에서 언제나 고정임을 뜻하지 않는다. 이 캡처 범위의 관측이다.

4. 보조 결과와 그룹 경계
chunk grouping에서도 norm은 score-calibrated fixed보다 총SSE0.134995% 악화했고 개선1/동점5/악화2였다.
frame과chunk의 같은 mixed 구성에 적용한 이 비교 방향은 일치한다.
회전-only frame/chunk의 오차 차이는 별도 그룹 규칙 효과로 보존한다. 기존 rollout의+0.54 MUSIQ를 head만의 효과로 되돌려 해석하지 않는다.

5. Claude 교차 검토에 대한 처리
A. SELFTEST.json의 예전 hash 지적: SELFTEST_v2.json에서 새 코드 hash와 전체 합성 검증을 확인했고 그 뒤 REGISTRATION_LOCK.json을 기록했다.
   따라서 실제 실행은 검증되지 않은 수정 코드를 사용한 것이 아니다.
B. 원시 SSE 합이 큰 층을 중심으로 평가한다는 지적: 범위 해석으로 수용했다. 주 질문은 현재 고정 선택보다 총 출력 손상을 더 줄이는가이며,
   그 질문의 사전 판정은 그대로 유지했다. 실행 후 기하평균으로 바꾸지 않았다. 모든 층별 비와 동점을 분리해 위 표에 보고했다.
   참고로 기하평균(norm/fixed)은 frame0.997540, chunk0.997215이지만 등록 밖 탐색적 보조이며 판정에 사용하지 않았다.
C. 정적 표와 비슷한 자료라 효과가 작을 것이라는 지적: 바로 그것을 확인하는 검사의 목적이었다.
   이 결과로 입력 적응 선택이 모든 설정에서 불필요하다고 주장하지 않고, 현재 후보의 추가 GPU rollout을 정당화할 이득이 없다고 판단한다.
D. 그룹 하나만 다르다는 이전 설명, norm head를 제외한 random, 층별 독립 p값 제안은 교차 검토에서 정정/철회됐다.

6. 범위와 검증 한계
- 모두 이미 개발에 사용한2개 프롬프트이고, 선정4층은 기존 관측을 보고 고른 것이다. 독립 보류 입력/모델 대표성/전체 생성 품질 검증이 아니다.
- CPU FP32 attention 기준이다. 원래 GPU native attention 대비 post-W_o NSE는8.20e-7~2.88e-6로 별도 저장했다.
  CPU 간 대조의 일치와 원래 GPU 실행의 비트 일치를 혼동하지 않는다.
- 이 실험의 전체7분은 여러 후보를 비교한 진단 비용이다. norm 또는 fixed 방법 자체의 실행시간/추론 오버헤드로 보고하지 않는다.
- 독립 감사의 첫 실행은 base payload의 JSON 필드를 잘못 참조해 KeyError가 났다. 감사 코드만 고쳐 AUDIT_RESULT_v2.json으로 재실행했다.
  원 실험은 정상 완료했고 RESULT.json, 등록 코드, 기준은 수정하지 않았다. 오류 기록은 AUDIT_ATTEMPT1_ERROR.txt에 보존했다.
