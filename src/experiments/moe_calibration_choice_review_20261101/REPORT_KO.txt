다음 후보: 적은 보정 자료에서 MoE 전문가의 GPTQ/RTN 선택
2026-11-01, 한국 시간

선택 결론

A를 작은 판별 검사의 우선 후보로 남긴다. 연구 주제나 새 알고리즘으로 채택한 것은
아니다. 기존 공개 규칙의 선택이 실제 입력에서 반대가 되는 조건을 확인했으므로,
그 차이가 품질과 보정 비용에서 중요한지 확인할 가치가 있다고 판단한다.
B의 보정 메모리 최적화는 주연구로 채택하지 않는다. 이번에는 GPU를 사용하지 않았다.
이전에 종료한 교차항 배분과 청크 합산 후보는 재개하지 않는다.

A. 보정 자료가 부족한 전문가에 GPTQ를 쓸 것인가, RTN을 쓸 것인가

누가 무엇을 결정하는가
  모델을 양자화하는 사람이 동일한 비트폭·그룹·저장 형식에서 전문가의 가중치를
  보정 자료로 수정할지(GPTQ), 원래 가중치를 직접 반올림할지(RTN) 결정한다.
  비트 배분은 바꾸지 않는다. 이번 질문은 양자화 방법 선택에 관한 것이다.

결정 시점에 알 수 있는 것
  원래 가중치, 보정 입력, routing, 전문가별 도달 토큰 수, 입력 차원, 보정 예산.
  별도로 떼어 둔 선택용 보정 문서의 실제 오차도 비용을 지불하면 사용할 수 있다.
  최종 평가 문서의 오차나 생성 품질로 방법·임계값을 고르면 안 된다.

이미 있는 관측
  [기존 실측 자료의 새 CPU 집계] OLMoE-0924의 8번 층, 기존 train 8문서의
  4,096토큰만 읽었다. 전문가 64개에 도달한 토큰 수는 최소48/중앙459/최대1,774다.
  캡처 파일 해시와 문서별 routing 원소 해시가 과거 감사 기록과 일치했다.
  quantization 오차, validation 출력, 가중치 후보는 이번에 읽거나 계산하지 않았다.

  [공개 규칙의 분석적 재생] 입력 차원을 K, 전문가 도달 수를 N_e, 전체 보정
  토큰 수를 N이라 하면, 확인한 규칙은 다음과 같다.
    GPTQModel의 기본 도달 비율 검사: N_e < 0.005*N이면 RTN.
    Olive의 기본 복합 검사: 위 조건 또는 N_e < 2*K이면 RTN.
  이는 고정 revision의 도달 수 검사를 재생한 것이며 두 패키지를 실행한 결과가 아니다.
  수치 분해 실패 등에 따른 추가 fallback은 포함하지 않았다.

                           K       비율 검사 GPTQ 대상    복합 검사 GPTQ 대상
    gate/up 입력          2,048           64/64                  0/64
    down 입력             1,024           64/64                  0/64

  비율 임계값은20.48토큰, 절대 임계값은각각4,096/2,048토큰이다.
  여기서 증명한 것은 '판단 불일치'다. GPTQ가 손상됐거나 RTN이 기회를 놓쳤다는
  증거는 아니다. 표본 수가 차원보다 적다는 사실만으로 GPTQ의 열세도 증명되지 않는다.
  기존 8문서는 이전 작은 진단을 위해 수집한 자료다. 통상적인 전체 모델 보정 규모를
  대표하지 않는다. 부족한 표본을 일부러 만든 뒤 일반적인 실패라고 주장하지 않는다.

가장 가까운 기존 방법과 강한 단순 기준선
  1. GPTQModel과 Olive는 이미 RTN fallback을 제공한다. '희귀 전문가에 RTN을
     쓰자', '표본 수를 고려하자'는 발상은 새 기여가 아니다.
  2. MoEQuant는 전문가 간 보정 불균형과 토큰-전문가 관련성을 다룬다.
     보정 데이터를 더 확보하거나 균형 있게 고르는 것도 기존 해결책이다.
  3. SARQC는 보정 오차와 원래 가중치에서의 변화를 함께 다루며, 부록 E.2에서
     보정 자료를 학습/선택 부분으로 나눠 정규화 강도를 고른다. MoE 평가도 있다.
  4. Nested-Ridge LOOCV의 2026-10-04 v8은 적은 표본의 damping 선택을 다룬다.
     동료 심사를 거치지 않은 사전 공개 논문이다. 원문의 강한 단순 비교군은
     실제 출력 오차를 보는 분할 검색이며, 그 검색이 일부 시간 비교에서 더 빠르다.
     따라서 '표본 수로 damping을 조절한다'거나 '작은 검증 집합으로 고른다'도
     새 방법으로 제시하지 않는다.

  첫 검사에는 고정 RTN, 고정 GPTQ, 두 공개 도달 수 규칙, 작은 실제 출력 평가를
  모두 포함한다. GPTQ의 damping을 하나만 고정해 놓고 그 실패를 새 문제로 부르지 않는다.

남은 질문과 실용적 의미
  상반된 규칙 중 하나가 이 조건에서 충분한지, 전문가별 선택을 달리할 실익이 있는지
  아직 모른다. 모든 전문가에 같은 설정이 충분하다면 그 설정으로 끝내면 된다.
  전문가별 선택이 도움이 되더라도 분할 검색으로 충분하면 새 선택기를 만들지 않는다.
  새로운 연구의 여지는 기존 강한 선택으로도 남는 손실 또는 비용을 확인한 뒤에만 생긴다.
  현재 문헌이 이 구체적 조건을 해결하지 못했다는 주장도 아직 하지 않는다.

작은 판별 검사안 — 아직 실행하거나 실험 등록을 완료하지 않음

  범위: 같은 층의 네 전문가, up 투영 한 개씩, INT4/group128, 나머지 연산 고정.
  전문가 선택: 기존 train 도달 수 순위의 8/24/40/56번째인43/62/51/17.
  선택 원인은 도달 수뿐이며 양자화 오차를 본 선택이 아니다.
  입력: 기존 train 기록 순서 앞4문서는 보정, 뒤4문서는 방법 선택,
        기존 validation16문서는 최종 확인. 각 분할의 도달 수를 다시 적용한다.
        기존 validation은 다른 연구에서 이미 사용한 자료이므로 새로운 맹검 자료가 아니다.
  후보: RTN과 GPTQ damping {0.01,0.05,0.1,1.0}, 전문가당5개, 최대20개 가중치 결과.
  통제: 같은 원래 가중치·보정 입력·양자화 형식·실제 payload bytes.
        공개 primitive를 고정해 비교하고, 서로 다른 패키지 전체의 우열로 부르지 않는다.
  기준선: RTN 고정, GPTQ 고정, 도달 비율/복합 규칙,
          선택용4문서로 모든 전문가에 공통 설정 하나를 고르는 방법,
          같은4문서로 전문가별 설정을 고르는 직접 평가.
  주 측정: 실제 routing으로 해당 전문가에 도달한 입력의 투영 출력 오차,
           각 규칙의 선택 손실, 준비·통계·모든 후보 생성·선택을 포함한 시간과 최대 메모리.
           투영 오차를 전체 MoE 블록 오차나 언어 모델 품질로 부르지 않는다.
           주 오차는 선택한 전문가의 모든 routed 입력에서 제곱 오차를 합산해 공통
           routed 원소 수로 나눈 값이다. 같은 입력에서 모든 정책의 분모를 공유한다.
           문서를 재표집할 때도 분자와 분모를 함께 합산한다. 실제 도달 입력이 없는
           분할은 유효성 미확보로 기록하며 추가 전문가로 교체하지 않는다.
  사후 최소오차 후보는 선택 손실을 설명하는 참고값이다. 배포 가능한 선택기나
  전역 최적 양자화기가 아니다. 최종 평가 문서로 정책을 선택하지 않는다.

  실행 전: 원래 BF16 투영과 무개입 경로 비교, 실제 패킹 왕복과 저장량 확인,
           CPU 독립 계산과 공개 GPTQ primitive 대조, BF16 수치 동점 기준 고정.
  실행 가능성: 가중치와 실제 입력은 로컬에 있다. Olive/GPTQModel은 설치돼 있지
              않으며 현재 환경에서 전체 패키지가 실행된다는 근거는 없다.
              다음 자원은 작은 primitive 비교의 실행 가능성을 확보하는 데 쓴다.
              환경 전체 업그레이드나 모델 재다운로드를 전제로 진행하지 않는다.

  제안 상한: 준비·검증·측정·보고60분, GPU단계10분, 가중치 결과20개,
             GPU allocated8GiB/CPU RSS8GiB/새 디스크512MiB, 먼저 도달하는 상한 적용.
  판정안: 선택용 문서에서 고른 전문가별 설정이 공통 설정 및 두 공개 규칙보다
          최종 투영 오차를5% 이상 줄이고 문서 단위 대응 구간의 하한이0보다 크며,
          native BF16에서도 수치 동점을 넘는 감소가 있어야 선택 이득을 인정한다.
          이는 후속 검토 기준이지 논문 채택 기준이 아니다. 기준은 실행 전 등록한다.
  종료: 한 고정 설정으로 충분하거나 이득이 없으면 해당 조건에서 선택기 개발 종료.
        직접 평가가 충분하면 그 방법을 사용하고 새 선택기 개발 종료.
        실행 유효성을 확보하지 못하면 미확보로 보고하고 커널 이식으로 늘리지 않는다.
  이득이 있어도 SARQC/LOOCV 등의 강한 방법과 비용까지 대조하기 전 신규성을 주장하지 않는다.

B. RTN으로 전환할 전문가의 Hessian을 먼저 수집하는 비용

  [공개 코드 관측] Olive는 전문가가 처음 관측되면 Hessian을 만들고, 자료 수집 뒤
  fallback 여부를 결정한다. 이번 도달 수를 같은 구조에 적용하면 두 입력 폭 모두
  최종적으로 RTN이지만, Hessian payload는 합계1.25GiB가 된다.
  이는 코드와 형상으로 계산한 payload이며 우리 GPU의 실측 peak/시간/OOM이 아니다.
  가장 단순한 대응은 RTN 고정 또는 먼저 도달 수를 세고 필요한 전문가만 보정하는 것이다.
  두 번째 방법의 추가 통과·전송·상태 보관 비용도 포함해야 한다.
  현재는 그 단순 대응으로 부족하다는 증거가 없으므로 주연구로 채택하지 않는다.
  A의 결과가 RTN으로 충분하다고 나오면 이 조건의 비용 문제도 기존 옵션으로 닫을 수 있다.

  문헌 보고: 보정 불균형과 적은 표본의 정규화·선택 문제 및 기존 해결법.
  미확인: 실제 선택 손실, 추가 선택기의 이득, 전체 모델 품질, 신규성, GPU 실행 성공.

  조사 범위는 여기서 끝내며 같은 근거로 다른 이름의 후보를 더 붙이지 않는다.
