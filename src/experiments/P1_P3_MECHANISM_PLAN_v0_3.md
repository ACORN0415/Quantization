# 메커니즘 실험 v0.3 — 진행 조건을 고정한 재생 진단

**상태: 미실행·미등록 초안. v0.1의 A−L 주 검정과 96궤적 실행안은 보류한다.**

속도·메모리·연산 계측은 [측정 보완 명세](MECHANISM_MEASUREMENT_SPEC.md)를 함께 따른다.
아래 진행 조건은 유지한다. 진단 포함 시간을 실사용 추론 속도로 보고하지 않는다.

| 항목 | 현재 결정 |
|---|---|
| 질문/주 대비 | 먼저 같은 BF16 쓰기에서 L→C-repeat→C-once를 대조한다. L은 물리 버퍼 그룹, C는 청크 내부 그룹이다. A는 주 개입에서 제외한다. |
| 진단 표본 | 기존 p00/p04 × 시드 101/202, INT4 우선, group 16/24/32. 새 보류 텍스트/시드는 사용하지 않는다. |
| 진단 결과 | attention 직전 같은 생존 토큰의 K/V 차이, encode 전후 변화, 그룹 ID·패딩·현재 쓰기 혼합, 실제 encode 횟수. 청크 0–6/7–41 및 층/호출별로 공개한다. |
| 진단 진행 조건 | 모든 게이트 통과 및 네 사례 모두 D16>10⁻⁶, D16−D24>10⁻⁶. 미통과면 이 계획의 자동 FR 없이 저장 진단을 정리한다. |
| 향후 주지표 | 아래 진행 조건 통과 시 L16 대 C-repeat16의 후반 **전체 raw 프레임 MUSIQ 하나**를 사용한다. 프롬프트 12개×시드 303/404, BF16/L16/C-repeat16 총 72궤적 후보를 고정하며 최종 게이트·비용·구현 해시 봉인 전에는 실행하지 않는다. |
| FR 검정 | 프롬프트별 시드 평균 차이, n=12, 양측 정확 부호 반전 검정 alpha=.05 하나, 95% 프롬프트 bootstrap 구간. |
| 보조 지표 | 경계 품질, 경계−내부 품질 차이, 시간 잔차·coverage·움직임·DINO. 모두 주지표와 구분한다. |
| 중지 규칙 | 토큰/호출 순서·동등 조건 게이트 실패, 비유한 주 상태, 메모리 예산 초과 시 원인을 기록하고 중지한다. 가설과 다른 결과는 구현 실패로 취급하지 않는다. |

## 실행 순서와 게이트

1. **선행 범위 점검 → 합성 쓰기 → 기존 BF16 쓰기의 스트리밍 재생** 순서로 진행한다.
2. C-repeat는 기존 과거 청크의 복원값을 다음 attention 전에 한 번 다시 encode한다.
   새로 과거로 넘어오는 pending은 그 뒤 최초 한 번만 encode한다. 같은 호출에서 최초
   encode와 반복 encode를 중복 적용하지 않는다. 각 read에 기여한 토큰의 encode 횟수를 추적한다.
3. no-quant 세 팔은 동일. C-once는 기존 P3, L은 기존 P1과 동일해야 한다.
   **g=24의 L/C-repeat는 동일 그룹·동일 read별 encode 횟수에서 bit-exact를 기대하는 게이트**다.
   실패하면 타이밍·상태 수명·padding을 조사한다. g=16/32의 L/C-repeat 값 차이는 진단 결과이며 실패가 아니다.
4. C-repeat/C-once의 고정 그룹 RTN 반복은 항등 또는 매우 작은 변화일 것으로 **사전 예측**한다.
   실제 BF16 계산·FP16 scale·실제 쓰기로 검사한다. 다르면 그대로 기록하고 보편적 항등성을 주장하지 않는다.
5. 그룹 크기는 한 번에 하나씩 재생하고 필요하면 층을 나눈다. 9개 전체 캐시를 동시에 GPU/CPU에 보관하지 않는다.
   실제 BF16 쓰기가 파일에 모두 저장돼 있는 것은 아니므로 재생용 teacher 실행의 비용도 먼저 잰다.

## 진단 전에 고정하는 요약값과 진행 조건

결정은 INT4, 기존 p00/p04 × 시드 101/202의 네 사례에만 적용한다. INT2와 g=32는 보조 진단이며
이들이 더 좋아 보인다는 이유로 주 판단을 바꾸지 않는다. 모든 층을 완료하기 전에는 진행 조건을 평가하지 않는다.

각 사례 i, 팔 a, 그룹 g, 종류 X∈{K,V}에 대해 attention 직전의 **과거 토큰만** 대응시킨다.
기준 B_X는 그 생존 토큰을 삽입했을 당시의 BF16 쓰기다. 현재 쓰기·퇴거 토큰·빈 패딩은 분자/분모에서 제외한다.
같은 전역 토큰 ID 순서로 정렬한 뒤 FP32에서 r_X=||stored_X−B_X||₂/max(||B_X||₂,10⁻¹²)를 계산한다.
각 청크에서 30층×5호출을 산술평균하고, 청크 7–41의 35개 평균을 다시 산술평균해 E_X(a,g,i)를 얻는다.
요약값은 E(a,g,i)=[E_K(a,g,i)+E_V(a,g,i)]/2다. K/V 각 값도 모두 공개하며 잘 나온 종류만 골라 판단하지 않는다.

D_g(i)=E(L,g,i)−E(C-repeat,g,i), H(i)=D_16(i)−D_24(i)로 고정한다.
진행 조건은 **모든 구현 게이트 통과 AND 네 사례 모두 D_16(i)>τ AND H(i)>τ**, τ=10⁻⁶이다.
τ는 재생 결과를 보기 전에 둔 상대 L2의 수치 허용치이며, 실제 영상 품질의 최소 효과 크기가 아니다.
g=24는 attention 직전 상태의 bit-exact 동등성 게이트를 별도로 통과해야 한다.

- 통과: 미리 정한 L16 대 C-repeat16 FR 계획만 최종 구현·게이트·봉인 단계로 넘긴다.
- 미통과: 자동 FR 생성 없이 전 진단과 부정 결과를 정리하고 이 계획을 종료한다.
- 게이트 실패/비유한 값/부족한 층·호출: 가설에 불리한 관측 결과로 세지 않고 구현/실행 미완료로 중지한다.
- 사례·seed 추가, g=32로 교체, τ 완화, K 또는 V만 선택해 조건을 통과시키지 않는다.
  다른 가설은 별도의 새 문서에 기록하며 이 진행 조건의 사후 성공으로 취급하지 않는다.

저장 계산은 입력에 대해 거의 결정적이지만 입력 내용에 대한 의존성이 사라지지는 않는다.
네 사례는 개발용 투자 판단 기준이지 메커니즘의 일반성이나 검정력을 보장하는 확증 표본이 아니다.

### 통과했을 때의 FR 후보를 미리 제한

새 프롬프트 12개와 두 시드는 예약한 파일을 그대로 사용한다. BF16 기준 24개와 L16/C-repeat16 각 24개,
총 72개 생성 궤적이다. 주 대비는 C-repeat16−L16, 후반 픽셀 249–500의 252개 raw 프레임 MUSIQ 평균이다.
시드 차이를 프롬프트 안에서 평균하고 n=12 프롬프트로 양측 정확 부호 반전 검정(4096조합, alpha=.05),
95% 프롬프트 클러스터 percentile bootstrap(20,000회, seed 872341)을 보고한다.
귀무가설 아래 짝 차이 대칭성/교환 가능성과 작은 편의 표본의 한계를 명시한다.
주 검정은 하나이며 경계·DINO·시간 잔차·그룹 크기 비교는 확증 검정에 추가하지 않는다.
비용을 감당할 수 없으면 새 보류 생성 전에 이 FR 안을 보류한다. 이 문서로 결과를 보며 표본을 줄이지 않는다.

## 저장 바이트와 실용적 주장 범위

g=16/24/32 비교표에는 각 팔의 유효 코드·패딩 코드·scale·BF16 pending/residual 바이트와 합계를 넣는다.
코드 전체에 패딩을 이미 포함했다면 패딩을 합계에 두 번 더하지 않는다. 부가 resident tensor는 별도 더한다.
같은 청크/호출 시점과 같은 살아 있는 토큰 수에서 측정하고, BF16 진단 원본·복원 임시 버퍼·모델 메모리는 별도 항목이다.
바이트 컨테이너의 실제 resident 값과 실제 코드를 pack했다고 가정한 추정치를 구분한다.
전체 peak VRAM을 순수 KV 저장량이나 저비트 커널의 메모리 절감으로 읽지 않는다.

g=24의 L/C-once 저장값이 가까워져도 그것만으로 생성 품질이 가깝다고 할 수 없다.
“이 RTN 구현·토큰 수·창에서 정렬되는 그룹을 쓰면 추가 저장 변화가 줄었다”는 조건부 지침을 우선한다.
실제 품질/메모리 동시 개선 주장은 해당 FR/실측 근거가 있어야 한다. g=24를 보편 최적값이나
모든 rolling 정책에 대한 규칙으로 일반화하지 않는다. 그 실용 질문을 새 FR의 주 질문으로 사후 교체하지 않는다.

## 해석의 한계와 다음 결정

- g=24는 4680과 32760을 나누므로 패딩·창 이동의 그룹 재편·현재-과거 혼합을 함께 제거한다.
  단, g 변경은 그룹 크기·구성원·scale 수·원래 양자화 오차도 바꾼다. **24에서 추세가 꺾이면 지지하는 패턴이지 단독 인과 증명이 아니다.**
  P3(C-once)와 C-repeat도 같은 세 크기에서 비교하고 정책×그룹 크기의 차이를 기술 통계로 공개한다.
- “그룹 크기가 커지면 품질이 반드시 단조 악화한다”는 가정을 하지 않는다.
  L→C-repeat는 청크 단위 그룹 규칙 개입으로 해석하며 eviction 위상만의 효과로 부르지 않는다.
- 진단 후 진행은 위에서 고정한 조건을 따른다. 원래 96개를 자동 실행하지 않는다.
- 경계 품질은 t=12c−3, c=21..41에서 t−2..t+2를 평가한다. 내부는 t+4..t+8로 고정한다.
  (C-repeat−L)의 경계 평균 차이에서 내부 평균 차이를 뺀 값을 보조 대비로 보고한다.
  경계 105프레임은 후반 전체 252프레임의 완전한 부분집합은 아니다. 최초 경계의 앞 2프레임(247/248)이 그 밖에 있다.
  위치별 움직임과 VAE 시간축 혼합이 달라 이 보조 대비도 시간 품질의 순수 인과효과는 아니다.

## 선행 연구 확인과 근거

[33-method 논문 본문·부록 A](https://arxiv.org/html/2603.27469v1)는 실제로 존재하며 기본 block size 16,
매 스텝 양자화·recent-BF16·refresh-only·여러 압축 정책을 설명한다. 확인한 논문 기술에는
이번 L/C-repeat/C-once × 16/24/32 정렬 재생 실험이 보고돼 있지 않다. 이것은 그 비교가
논문에 명시돼 있지 않다는 확인이며, 관련 저장소 모든 이력이나 전체 선행 연구에 대한 신규성 보증은 아니다.
[QVG](https://arxiv.org/html/2602.02958v1)는 이미 청크당 단회 압축으로 재압축 드리프트를 피한다고 명시한다.
따라서 개발 투자 전 관련 구현 범위와 차별점도 대조한다. 투고 수준을 미리 약속하지 않는다.

refresh-only와 P3는 같다고 가정하지 않는다. 논문 부록 A의 refresh-only는 clean-context refresh 때
캐시를 양자화하는 cadence이며, 오래된 영역이 이후 refresh에서 다시 encode될 수 있다.
이 연구의 P3는 완료된 청크를 과거로 넘길 때 한 번 encode하고 남아 있는 그 state를 재사용한다.
즉 호출 빈도 제한과 저장 청크 수명 전체의 단회 encode는 다른 조건이다. 로컬 생성 스크립트의
cadence 설정은 확인했지만 이 문장으로 upstream 모든 실행 경로의 동등성을 검증했다고 주장하지 않는다.

[v0.1 상세안](P1_P3_MECHANISM_DRAFT.md)은 설계 이력/미실행 참고용이다. raw 평가·압축 민감도·보관 원칙은 참고하되
이 문서의 A 제외·단일 주지표·조건부 72궤적 후보 결정을 우선한다. 측정·개발 진단 실행은 이 초안 수정만으로 시작하지 않았다.
