Causal VAE 저장 feature state 양자화: 독립 문헌·소스 판별
작성자: Codex /root/method_gap_codex
조사 시작: 2026-11-05 17:36:48 UTC. 등록 절대 마감: 18:06:48 UTC.
범위: 원문 4편, 공개 저장소 1개, 로컬 소스·기존 JSON만 읽음. GPU/VAE/모델/텐서 로드/새 점수/가중치 다운로드/소스 수정/커밋 0. 외부 자료는 메모리와 도구 출력으로만 읽어 디스크 근거 캐시 0B. 이 보고서 외 산출물 없음. 실제 Opus 독립 결론을 열람하지 않았다.

판정
현재 저장 state 양자화를 새 연구로 채택하지 않는다. native 상태는 작지 않지만, 현재 실행에 필요한 메모리·시간 요구를 위반했다는 관측이 없고, 더 단순한 BF16 출력 스트리밍도 비교하지 않았다. LightVAE는 이미 투영된 시간 이력을 저장하며, 일반 recurrent state 저비트 양자화도 선행연구가 있다. 'Wan의 상태를 INT8로 저장한다'는 설정 차이만으로 남는 방법론 공백을 확보하지 못했다.

다음 자원을 쓴다면 손실 압축 개발 대신, 동일 산술의 BF16 출력 스트리밍을 기존 native 경로와 한 번 비교하는 실행 정리로 제한한다. 이것은 새 양자화 방법을 위한 성공 판정이 아니라, 알려진 출력 버퍼 중복을 제거한 강한 기준선을 확보하는 일이다. 실제 메모리 요구가 없는데 임의로 작은 예산을 만들어 상태 압축을 필요하게 만들지 않는다.

1. 실제 관측과 아직 없는 근거

직접 읽은 기존 RESULT.json의 한 입력 결과:
- BF16 복원 28.836966초, FP32 복원 79.574704초. 새 generator 0, VAE 2회였던 완료 진단이다.
- BF16 첫 팔의 프로세스 누적 GPU allocated peak 5,727,909,376B = 5.335GiB. reserved peak는 13.488GiB이다. reserved와 live tensor payload는 다르다. 첫 팔 수치에는 준비/복원/출력 처리 등이 포함되고, feature state만의 피크가 아니다.
- 후반 동일 latent RGB RMSE 0.0015816216으로 기존 .02 engineering sensitivity 기준 미달, precision expansion 종료. 이것은 BF16과 FP32의 해당 경로 차이가 작다는 근거일 뿐 INT8 state의 안전성·의미 품질 보존 근거가 아니다.
- 현재 24GB에서 이 BF16 입력은 실행됐다. VAE 상태 때문에 발생한 OOM, 실제 동시 실행 메모리 상한, 상태 전송/복원 시간 비중은 없다.

소스 직접 확인:
- vae.py:28–36은 이전 convolution 입력 이력을 현재 입력에 연결한다. :202–217은 다음 호출에 필요한 꼬리를 clone/cat해 보존한다. 이력은 일반 SSM의 무한 반복 hidden-output recurrence와 동일하지 않다. 고정 깊이 causal CNN의 입력 이력이며, 양자화 오차가 이후 층·시간으로 전달될 수는 있어도 Mamba의 오차 누적 분석을 그대로 적용할 수 없다.
- :545–569는 latent 126개를 순차 decode하면서 결과 out을 반복 torch.cat한다. 끝에 state를 clear한 뒤 반환한다.
- wrapper:105–108은 전체 결과를 FP32로 바꾸고 clamp한 뒤 다시 stack한다. CPU로 완료 슬랩을 넘기는 진정한 출력 스트리밍이 아니다.
- cached_decode는 호출 간 상태를 유지하므로 명칭만 보고 use_cache=False를 '시간 상태를 사용하지 않음'으로 해석하면 틀린다. native decode도 내부 시간 캐시를 사용하고 시작·종료에 초기화한다.

2. 상태 payload의 정적 산술 추정 — 총 peak 측정 아님

전제: 실제 wrapper z_dim=16, _video_vae의 dim=96, dim_mult=[1,2,4,4], residual block 수 2, temporal_downsample=[False,True,True]. Decoder가 반대로 받아 temporal_upsample=[True,True,False]가 된다. B=1, latent 126×60×104, 출력 501×480×832. CACHE_T=2, BF16 원소 2B, inference_mode/no_grad 조건이다. 기본 Decoder 생성자에 적힌 다른 temporal 기본값을 적용하지 않았다.

두 번째 latent 이후 정상 상태의 살아 있는 feature tensor 32개:
- 60×104: 12개, 105,830,400B.
- 120×208: 7개, 249,200,640B.
- 240×416: 6개, 460,062,720B.
- 480×832: 7개, 1,073,479,680B.
합계 1,888,573,440B = 1.758871GiB. list는 count_conv3d에 의해 33칸이지만, shortcut의 1×1 causal conv가 실제 시간 이력 갱신 경로에 들어가지 않아 1칸은 사용하지 않는다. 첫 latent에는 두 temporal upsampler가 'Rep' 표식이며 나머지 꼬리가 1프레임이라 920,325,120B다. 최종 고해상도 7개가 정상 state payload의 약 56.84%라는 것은 정적 분포이지 병목의 실측이 아니다.

이 산술은 부모의 코드 추적과 native helper의 독립 소스 추적이 일치했다. 실제 tensor 수명/allocator로 재검증한 값이 아니다. 상태 꼬리는 clone/cat 소유 storage여서 view가 전체 activation을 붙잡는 경우를 가정하지 않았다. convolution 중에는 구/신 상태·연결 입력·padding·출력 등이 겹치므로 전체 peak와 다르다.

BF16→INT8 저장만 가정하면 raw state payload 절감의 낙관적 한계는 944,286,720B = 0.879436GiB이며 metadata, pack/dequant workspace를 빼기 전이다. 실제 GPU peak 감소의 상한이라고 부르지 않는다. FP32이면 같은 정적 state는 3.517742GiB지만 앞선 FP32 전체 peak와의 차이를 이 항 하나에 귀속할 수 없다.

501프레임 RGB 한 벌의 FP32 payload는 2,400,952,320B = 2.236061GiB이다. wrapper float/stack에서 두 벌이 함께 살아 있을 수 있고, decoder의 반복 cat도 구/신 BF16 출력이 겹친다. 다만 decode는 wrapper float/stack 전에 cache를 clear하므로 이 모든 수치를 그냥 더하면 틀린다. 상태 크기는 고정 해상도에서 영상 길이에 대해 일정한 반면, 누적 RGB 보관은 길이에 비례하고 반복 cat의 총 복사량은 늘어난다.

3. 가장 가까운 선행연구와 실제 공개 코드 범위

[1] LightVAE, arXiv:2610.14726v1, 2026-10-10.
https://arxiv.org/html/2610.14726v1
§4.1–4.3 및 Appendix C를 확인했다. 현재 항은 dense로 유지하고 과거 temporal kernel을 저랭크화한다. Q_j,t=B_j X_t를 계산해 시간 이력으로 저장하고, 현재 항과 A(Q_1,t-1+Q_2,t-2)를 합친다. block pruning과 teacher 기반 복원 학습도 사용한다. 즉 weight만 줄이는 방법이 아니라 저장되는 역사 표현 자체를 바꾼다. 고정 원모델의 raw feature를 INT8로 저장하는 개입과 같지는 않지만, 'VAE 시간 상태의 압축'이라는 넓은 신규성 주장은 막힌다.

공식 저장소 1개만 확인: ModelTC/LightVAE, commit 38b0587d47df9188e3e05973265352962b20ada4.
https://github.com/ModelTC/LightVAE/blob/38b0587d47df9188e3e05973265352962b20ada4/lightvae/tlr.py#L52
실제 z는 2r채널, cache는 마지막 두 temporal 위치이므로 [B,2,2r,H,W]이다. 원래 [B,C_in,2,H,W]와 같은 dtype이면 4r 대 2C_in 원소여서 r<C_in/2일 때에만 그 항의 저장량이 감소한다. 투영이라는 이유만으로 모든 rank에서 메모리가 감소한다고 해석하지 않는다. rank0은 해당 상태를 제거하나 모델 근사를 바꾼다. kernel은 BF16 cache 경로를 포함한다.
modules.py와 base Wan decoder는 결과를 list에 모아 마지막에 cat한다. 반복 cat을 없앤 기존 단순 기준선이지만 전체 GPU 출력 보관은 남으므로 CPU 출력 스트리밍과 구분한다. 저장소의 H3 INT8 변환은 transformer weight 대상이며 이를 Wan temporal feature cache INT8 구현으로 세지 않았다. RTX4090 실행/성능/품질은 검증하지 않았다.

[2] LatentQuant, arXiv:2610.03959v1, 2026-10-02.
https://arxiv.org/html/2610.03959v1
§3.2·§5·Appendix A/E/F의 관련 부분을 확인했다. conv/linear의 NVFP4 W4A4와 활성 scale/packing, encoder latent-interface 및 decoder 적응을 다룬다. FP32 master/optimizer와 일부 고정밀 연산이 남는다. 'resident VAE model state' 표는 모델 가중치 및 미양자화 모델 상태를 포함하고 activation/output scratch를 제외한다. 이를 persistent temporal feature cache 압축량으로 읽으면 안 된다. 읽은 범위에서 cache write/read 정밀도 계약은 확정하지 못했다. 그 미기술이 새로운 기여의 증명은 아니다. native NVFP4 실행과 현재 RTX4090의 저장 INT8→BF16 convolution 경로도 다르다.

[3] Cache-Aware Conv3D Lowering, arXiv:2609.31938v1, 2026-09-25.
https://arxiv.org/html/2609.31938v1
§3–7의 cache/lowering·유효성·메모리 결과를 확인했다. 기존 가중치와 temporal cache 의미를 유지하며 causal 3D convolution을 temporal tap별 2D convolution으로 바꾼다. 실수 산술에서는 동등하지만 유한 정밀도 bit identity는 별도다. 지원 shape/stride/group을 검사하고 fallback한다. Jetson 결과이므로 우리 GPU 속도를 예측하지 않는다. §6.4 clean 17-frame의 peak가 native 5.37GiB→lowered 7.31GiB로 증가했다. 따라서 강한 latency 기준선이지만 메모리 문제까지 해결한다고 보장하지 않는다. 이 논문의 공개 코드는 이번 저장소 1개 제한 때문에 확인하지 않았다.

[4] Q-Mamba, Findings of ACL 2025, 공식 문서 2025.findings-acl.551.
https://aclanthology.org/2025.findings-acl.551/
https://aclanthology.org/2025.findings-acl.551.pdf
공식 PDF의 DSQ/ESR 설명과 해당 실험 부분을 메모리에서 text 변환해 읽었다(전체 부록 전수 검토 아님). DSQ는 state/channel 축 scale로 SSM hidden state를 양자화하고, ESR은 quantization을 반영한 선택적 복원을 다룬다. weight/operand activation만의 양자화와 달리 persistent state가 직접 대상이다. W8A8H4 및 plain MinMax 계열 대조가 있어 'recurrent state를 저비트로 저장한다'는 일반 발상은 선행연구와 겹친다. Wan의 convolution 입력 꼬리와 Mamba의 recurrent hidden state는 다른 동역학이므로 reported 안전성/장기 오차를 그대로 옮길 수 없다. 코드 저장소는 열지 않았다.

4. 단순 해결책이 우선인 이유와 한계

가장 먼저 둘 기준선은 원모델·원BF16을 유지하고 RGB 출력만 CPU로 순차 내보내는 경로다. latent denormalization, 전체 conv2 호출, 126개 decoder 호출의 순서·형상·cache reset 시점을 유지해야 한다. 단순히 cached_decode를 latent 한 개씩 호출하면 conv2 연산 형상도 달라질 수 있어 같은 산술이라고 전제할 수 없다. 출력 slab의 float/clamp를 동일한 GPU 산술로 처리한 뒤 CPU로 보내고, GPU list에 전체 결과를 계속 쌓지 않아야 한다.

spatial tiling은 현 middle AttentionBlock의 전역 spatial attention까지 임의로 잘라 exact라고 할 수 없다. convolution halo, attention 범위, temporal state와 경계가 동일한 구현인지 확인해야 한다. 이번에는 추가 공개 repo를 열지 않았으므로 실행 가능한 exact tiling을 확보했다고 주장하지 않는다. 기존 exact Conv3D lowering 역시 이 GPU에서의 비용과 peak를 따로 확인해야 하며 memory 대체재라고 간주하지 않는다.

실제 부족이 남을 때에만 plain INT8 state RTN이 더 복잡한 보정/배분보다 먼저일 기준선이다. 비교 시 scale·padding·실제 packet bytes, chunk write/read 시점, 복원 임시 버퍼, 원출력 오차, 전체 복원시간을 포함해야 한다. 상태만 INT8이고 convolution이 BF16이면 Tensor Core FLOPs가 줄었다는 주장은 안 된다. 이 단계조차 이번에 실행하지 않았다.

5. 아직 남는 중요한 선택 하나와 다음 자원 배분

선택 주체: 정해진 해상도·동시 실행 요구에서 VAE를 배포하는 구현자.
선택: '동일 출력 BF16 스트리밍 후에도 실제 GPU 메모리 요구를 충족하지 못해, 저장 feature state에 손실 압축을 허용해야 하는가?'
선택 시 사용 가능한 정보: 입력 형상, 모델·cache schema, 실제 deployment memory/time 요구, 보정용 독립 입력, 계측된 상태/출력/임시 버퍼 수명. 최종 평가 입력의 품질 결과를 이용해 방식이나 상한을 사후 선택하면 안 된다.
현재 가장 강한 단순 선택: 해당 24GB 단독 복원은 native BF16로 가능하므로 고정 BF16를 유지한다. 메모리를 줄일 때는 원출력 스트리밍부터 정리한다. 현재 실자료에는 이 선택이 실패한다는 증거가 없다.

따라서 새 state 양자화 방법 후보는 없음. 다음 자원을 배정한다면 아래 실행 정리 검사 하나만 권한다. 지금 이 보고서는 실행 승인이 아니다.
- 목적: 출력 보관을 바꾼 BF16 경로가 원출력과 같고 실제 peak/시간을 줄이는지 확인. lossy method 검사가 아니다.
- 입력/팔: 동일 기존 latent 1개, native BF16와 출력 streaming BF16 총 2회. 동일 checkpoint·원 denorm/conv2/decoder 산술·TF32/autocast/cache 규칙. generator/VAE 정밀도 팔/새 데이터 없음.
- 검증: 전체 501프레임의 shape/dtype/원소 bytes를 CPU에서 비교한다. 출력 형상·순서·cache reset·126 decoder 호출을 기록하고, 첫/정상/마지막 단계의 unique state storage와 전체 allocated/reserved peak를 분리한다. 각 팔 새 프로세스 또는 peak 기준을 완전히 분리한다.
- 자원 제안: root가 별도로 등록할 때만 GPU 직렬 1개, VAE 2회, 전체 10분, CPU4, RSS12GiB, GPU allocator22GiB, 저장≤256MiB. 전체 RGB는 CPU 메모리 비교 뒤 해제하고 새 영상을 저장하지 않는다. 중간 복제/상주 입력까지 해당 상한에 포함한다.
- 유효: 동일성 및 실행 계약·자원 상한 통과. 출력 정리가 peak/시간을 얼마나 바꿨는지 그대로 보고하며 임의 5%/10%를 연구 성공으로 만들지 않는다.
- 실패/무효: 출력 불일치는 이 exact-streaming 구현을 무효 처리하고 precision threshold를 완화하지 않는다. timeout/OOM/누락 계측도 판단 불가이며 자동 재시도·양자화 팔 추가 없음.
- 종료/다음 판단: 실제 deployment 요구를 native 또는 streaming BF16가 이미 충족하면 state 양자화 개발 종료. 명시된 요구가 계속 미달하고, 상태 payload 절감이 그 부족을 메울 현실적 여지가 있을 때만 plain INT8 RTN을 별도 검토한다. 요구 자체가 없는 현재 상황에서는 검사 결과가 좋아도 새 양자화 연구로 승격하지 않는다.
