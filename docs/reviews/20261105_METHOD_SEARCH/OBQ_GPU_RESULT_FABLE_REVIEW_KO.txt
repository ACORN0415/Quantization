== fused 단계 범위에 대한 의견 ==
보고서 3항(먼저 owned packet·수명 검사·GPU 전처리 정의 확정)과 주 작업자 계획(fused + owned graph 대조)은 충돌하지 않는다. 한 등록에 세 묶음을 넣되 순서를 고정하면 된다:
 (a) owned-output graph: replay() 안·capture 밖 clone, eager도 같은 소유권 정책(packed·scale·sentinel), 서로 다른 두 입력 연속 replay 후 첫 패킷 불변. 비용 작고 필수.
 (b) GPU-native 전처리 변형: GPU 회전·scale 위에서 코드 동등성 + 4 endpoint 출력 감소 gate. "CPU 이식 비트 성공"이라 쓰지 않음.
 (c) fused(warp 1행·4warp 블록·레지스터 상주·니블 패킹 융합): CUDA C++ load_inline, 컴파일 ≤ 2, `-fmad=false`(또는 __fmul_rn/__fsub_rn), IEEE 나눗셈, rintf, 연산 순서 동일. Triton은 FMA 축약 제어가 불확실해 비트 일치 요구와 맞지 않음.
     사전 실패 기준: eager/owned graph와 packed 비트 불일치 → 튜닝 없이 종료·원인 기록; 일치하되 owned graph 대비 2배 미만 → 중단. GPTQ lazy-batch 블록화는 비트 불일치이므로 정확 tier로 쓰지 않음.
 (a)(b)가 실패하면 (c)를 돌리지 않는다. 45분·2 cases·생성 0은 적절. 성공해도 커널 공학이지 기여가 아니다.

== 미확인 ==
GPU 값 재실행 없음. 메모리 바운드 해석은 왕복량 추정에 기초한 가설이며 프로파일(ncu) 미실시. 이 검토는 승인이 아니라 권고다.

== 정정(주 작업자 지적 수용, 2026-11-05) ==
1. "eager에서 event ≈ host → 커널 실행 지배"는 틀렸다. CUDA event 구간은 같은 스트림의 start/end 마커 사이 GPU 타임라인이며 host launch 대기로 생긴 공백도 포함한다. 따라서 event≈host는 자명하고
   launch 대기 유무를 말해 주지 않는다. 말할 수 있는 것: graph replay는 커널 사이 host launch가 없으므로 graph 4.92 ms는 커널 실행(+graph 오버헤드)에 가깝고, eager−graph ≈ 3 ms가 launch 공백·allocator의 상한이다.
2. "왕복 3.7 GB / 4.9 ms ≈ 750 GB/s → 메모리 바운드, compile로 못 줄이고 fused만 가능"은 과장이다. 3.7 GB는 측정이 아니라 단계별 슬랩 크기의 산술 추정이며 프로파일(nsys/ncu) 없이는 병목을 확정할 수 없다.
   또한 torch.compile(inductor)은 단계당 분리 연산(div·round·clamp·mul·sub·mul·sub)을 1~2 커널로 융합해 슬랩 왕복 횟수를 줄일 수 있으므로 배제할 수 없다(단, inductor 생성 커널의 FMA 축약으로 비트 일치가 깨질 위험은 사전 명시 필요).
   정확한 서술: "메모리 병목 가설(미프로파일). 단계별 전역 슬랩 왕복을 없애는 쪽(레지스터 상주 fused)이 가장 큰 폭, compile 융합은 중간 폭 후보".
3. "fused가 owned graph 대비 2배 미만이면 중단"은 제 제안이며 등록되지 않았다. 판정은 전체 encoder 개선·비용으로 한다는 root 입장에 따른다.
4. stage 2 설계 동의: RTN은 eager/graph 둘 다 허용, OBQ graph는 U도 매 호출 static 복사(786 KB, timed 포함)해 30층이 한 graph를 공유 가능하게 하고 출력 clone 포함. 새 커널의 배포 기여는 자동 확정하지 않음.
