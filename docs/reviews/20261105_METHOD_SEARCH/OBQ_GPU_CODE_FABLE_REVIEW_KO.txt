== 추가 검토 2: graph 출력 수명 결함(root 발견)과 보완안 ==
- 결함 확인: graph 모드 replay()는 capture private pool의 `out`을 반환하므로 다음 replay가 이전 패킷을 덮어쓴다(176-178행 구조). 벤치마크는 즉시 비교라 통과하지만, 배포 encoder는 청크마다
  소유(owned) packed/scale을 캐시에 남겨야 하므로 D2D 복사(packed 3.6 MB + scale 0.9 MB + sentinel)가 실제 청크당 비용의 일부다. root 지적이 맞다.
- 보완안 평가: `return tuple(t.clone() for t in out)`를 timed 범위에 넣는 것은 타당. 단 두 가지 조건:
  (1) clone은 captured 함수(execute) 안이 아니라 replay() 안에서 graph.replay() 뒤에 해야 한다. capture 안에 넣으면 clone 대상도 private pool이라 똑같이 덮어써진다.
  (2) eager 모드와 대칭을 맞출 것. eager의 packed는 매 호출 새 할당이라 이미 owned이지만, T_code의 scale은 입력 `s`를 그대로 반환(borrowed)한다. 두 모드 모두 같은 "owned 패킷" 정책
      (packed·scale·sentinel clone)으로 통일해야 paired 차이가 출력 정책 차이를 포함하지 않는다. 추가 복사는 4.5 MB D2D로 수십 µs 수준이라 결론을 바꾸지 않을 것이나 대칭이 중요.
- 검사안 평가: 서로 다른 두 입력을 연속 replay한 뒤 첫 패킷 불변 검사는 결함을 직접 잡는 올바른 검사다. 합성 입력은 같은 형상·dtype의 자료 유도 입력(예: z와 −z)을 쓰고 static x를 건드리지 않아야 한다.
  CPU selftest로는 graph를 검사할 수 없으므로 GPU worker의 타이밍 전 단계에 넣는 것이 맞다.
- 이미 run이 시작된 경우의 처리(측정을 borrowed output 한정으로 표기, 후속 별도 등록)도 적절. 고정 코드 연산·bit gate 불변에 동의.

== 추가 검토 3: GPU 비용 1단계 결과(주 작업자 보고 수치 기준, RESULT 파일 미열람)와 다음 자원 판단 ==
수치(host 중앙값, 층·청크당): T_code RTN 0.148 ms / OBQ eager 7.9 ms / OBQ graph(borrowed) 4.93 ms. T_encoder 4개 unsupported(회전 불일치 1069~1117/7.2M, scale 11~12/451k — 예측대로).
30층 외삽(추정, 실측 아님): eager 238 ms, graph 148 ms/청크 → rollout 청크 1.95 s 대비 12.2% / 7.6%, 참조 소비자 청크(1.09~1.69 s) 대비 14~22% / 9~14%.
graph 4.93 ms = 단계당 38 µs. 단계마다 남은 열 전체(평균 64열 × 4680 × 12 × 4 B)를 읽고 쓰므로 약 3.7 GB 왕복 → 메모리 바운드이지 launch 바운드가 아니다. 따라서 Graph로는 더 못 줄이고,
전역 workspace를 없애는 융합 커널(행을 레지스터에 유지)만이 다음 자릿수(<0.5 ms 기대)를 연다. 주 작업자의 "fused 가치 있음" 판단에 동의.
필수 조건·반론:
 1. 비트 일치 요구를 유지하려면 Triton이 아니라 CUDA C++(load_inline, 컴파일 ≤2)로 쓰고 `-fmad=false`(또는 __fmul_rn/__fsub_rn 명시)와 IEEE 나눗셈(기본 -prec-div=true), rintf(half-to-even)를 써야 한다.
    eager는 mul·sub·div·round가 각각 별도 IEEE 연산이므로 FMA 축약이 생기면 마지막 비트가 바뀌어 코드가 뒤집힌다. 연산 순서도 동일하게: c=rint(w_j/s_j); e=(w_j − c·s_j)/u_jj; w_k −= e·u_jk(역수 곱 금지).
 2. GPTQ 표준 lazy-batch(블록 32 + matmul 갱신)는 수학적으로 같지만 합산 순서·cuBLAS FMA 때문에 비트 일치가 아니다. "정확 tier"로 쓰지 말 것. 쓰려면 별도 산술 변형으로 등록.
 3. 패킹 융합은 common.pack의 레이아웃(메모리 순서상 인접 dim 쌍 → 같은 (token, head)의 연속 dim)과 일치해야 한다. lane이 연속 dim을 들면 레지스터에서 바로 니블 패킹 가능.
 4. 실패 기준(사전): 융합 커널이 eager/graph와 packed 비트 불일치 → 튜닝 없이 불일치로 보고하고 종료(원인 FMA/순서 기록). 비트 일치하되 graph 대비 2배 미만이면 추가 개발 중단.
    성공해도 "GPTQ 커널 공학"이며 논문 기여로 쓰지 않는다(기존 합의).
 5. native GPU 전처리 변형(회전·scale을 GPU에서 계산) 별도 등록에 동의. 이름은 "GPU-native 산술 변형"으로 하고, 같은 GPU 전처리 위에서 코드 동등성 + 4 endpoint 출력 감소 gate를 적용.
    CPU 이식 비트 성공으로 서술하지 않는다. scale 불일치 11~12개는 그룹 absmax 동점 원소의 회전값 차이로 설명 가능(가설).
 6. owned 출력 clone·static factor 교체 비용 포함, 2입력 연속 replay 불변 검사 필수 — 동의.
