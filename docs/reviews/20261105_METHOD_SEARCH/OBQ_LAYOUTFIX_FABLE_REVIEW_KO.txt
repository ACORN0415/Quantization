== 1. 원인 판정: 수명 버그 아님, 전처리 행렬곱의 dispatch 차이 — 근거 충분 ==
- 네 구현 모두 첫 출력 보존·출력 주소 독립·원본/factor 보존 → owned 수명 계약은 정상. eager/fused는 두 입력 모두 참조와 정확 일치. Graph 두 구현만 두 번째 입력에서 불일치(RTN_graph packed 9/scale 6, OBQ_graph packed 396/scale 6).
  OBQ 쪽 packed 불일치가 큰 것은 순차 보상의 행 내 전파와 양립(동일 scale 6 불일치).
- 별도 전처리 검사: 첫 입력은 Graph/eager z·scale 정확 일치, 두 번째 입력은 z 1080·scale 6 불일치, eager 반복 2회는 자기 일관. → "모드 차이"가 아니라 "입력 텐서의 layout 차이"가 원인이라는 설명과 일치.
- layout: 원본 K와 Graph static K의 stride [50319360,1536,128,1](32760×1536 = 전체 7청크 캡처 버퍼의 view), 두 번째 입력은 [7188480,1536,128,1](새 할당). 둘 다 is_contiguous()=True이나 선행 singleton 차원의 stride만 다르다.
  PyTorch 2.6 ATen should_fold(LinearAlgebra.cpp)는 선행 차원을 접을 수 있는지 stride 곱 관계로 판단한다. 50319360 ≠ 4680×1536 → 접지 못해 bmm(배치 1), 7188480 = 4680×1536 → 접어서 mm.
  CPU profiler에서 원본은 aten::bmm, 변형은 aten::mm 호출을 확인(보고서). cuBLAS에서 gemmStridedBatched(배치 1)와 gemm은 다른 커널/누산 순서를 쓸 수 있으므로 FP32 결과의 마지막 비트가 달라지고
  BF16 캐스트 경계 원소(1080/7.2M ≈ 1.5e-4, stage1의 CPU-GPU 불일치와 같은 자릿수)가 뒤집힌다. GPU 커널 트레이스는 없으므로 "가설에 구체 근거가 있음" 수준으로 서술한 보고서 표현이 적절하다.
- 따라서: (a) 커널·OBQ 수학·소유권에는 결함 없음, (b) 전처리의 수치 정의가 입력 layout에 의존했다는 설계 결함, (c) 이전 envfix의 실패 판정은 그대로 두는 것이 맞다(등록 기준 미완화).
- stage1 T_encoder의 CPU 불일치(1117/1069)도 같은 bmm 경로였으나 그건 CPU MKL 대 GPU 차이이고, 이번은 GPU 내 bmm 대 mm 차이다. 두 사실을 섞어 쓰지 말 것.

== 2. layoutfix 수정 정의의 타당성: 타당, 단 "새 GPU-native 전처리 변형"으로 등록해야 함 ==
- 수정: 공통 gpu_frames를 `k.reshape(-1,128).float() @ H` 후 원형상 복원으로 명시. reshape(-1,128)은 singleton-stride view에서도 [N,128] stride [128,1]의 2D view가 되므로 모든 입력이 같은 mm 경로를 탄다 → dispatch가 layout에 독립. 올바른 처방.
  `.contiguous()`만으로는 고쳐지지 않는다는 보고서 지적(이미 contiguous라 no-op)도 맞다.
- 비교 타당성: (i) 품질 3팔(R_bf16/R_fp32/O_gpu)이 모두 같은 새 gpu_frames를 쓰므로 팔 간 공정성 유지. (ii) T_encoder 타이밍의 RTN/OBQ도 같은 전처리라 paired 차이 유효; bmm→mm 비용 차이는 양 팔 공통이며 미미.
  (iii) T_code는 stage1 동결 CPU z/scale을 입력으로 쓰므로 영향 없음 — T_code 정확 일치 결과는 그대로 유효. (iv) 이전 stage2/envfix에서 품질·타이밍 결과가 전혀 나오지 않았으므로 "결과를 본 뒤 조건 변경"이 아니다.
  (v) 다만 GPU 전처리 값 자체가 바뀌므로(bmm 반올림 → mm 반올림) 이전 GPU-native 정의와 다른 변형이다. 등록문에 "mm 경로 명시 전처리 변형"으로 적고, 4 endpoint 20% gate·exact code·수명 검사를 전부 다시 통과해야 한다(주 작업자 계획과 일치).
- 기준 완화 없음 확인: 허용오차 도입 없음, gate 수치 불변, 팔·반복 횟수 불변, 원 절대 마감 유지. 적절.
