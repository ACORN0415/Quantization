1. 결과 타당성 — 판단: 등록 기준 안에서 타당. 단, 아래 범위 제한을 붙여야 한다.

확인한 수치(RESULT.json):
 층18: SSE 480.77(BF16 RTN) / 484.64(FP32 RTN) → OBQ_FULL 289.67. 이득 39.7% / 40.2%. K-only 참조 기준 342.3→154.2(55%).
 층24: 133.10 / 137.19 → 89.47. 이득 32.8% / 34.8%. K-only 88.5→44.6(50%).
 OBQ_DIAG == FP32 RTN(코드 해시 동일), payload 54,097,926B 네 팔 동일, RSS 2.5GB, 18.6초. 등록 lock 해시 일치(AUDIT).
 K 텐서 SSE는 +61% / +53% 증가하면서 logit MSE −47% / −41%, 출력 SSE −40% / −33%. 즉 "재구성 오차 ↑, 출력 오차 ↓"가 세 번째로 재현됐다(회전, 예측 코딩에 이어).
 cpu_vs_native NSE 2.5–2.8e-6: CPU FP32 참조와 GPU native 출력 차이는 효과(1e-3 수준)의 1/1000 → 참조 유효.
 V4 바닥: v_only NSE 1.27e-3(층18), 0.91e-3(층24). 전체 참조 기준 sse에서 V 바닥이 차지하는 비중이 층18 28%, 층24 34%로, 내가 이전 검토에서 추정한 "최대 7%"보다 훨씬 크다(정정). 그래서 K-only 참조 이득(55/50%)이 전체 참조 이득(40/33%)보다 크다. 등록 주지표는 전체 참조이므로 판정은 그대로, 보고에는 둘 다 적을 것.
타당성에 대한 반론 검토:
 (a) 격자 악용? 동일 grid [-8,7]·동일 scale·동일 payload assert 통과. 코드 변경 17%(7.4M/43M). 악용 없음.
 (b) 우연? 두 층 모두 같은 방향·비슷한 크기이고 logit MSE까지 일관. 다만 층 2개·prompt 쌍 1개·읽기 1회(청크7 call0, q 128개)다. 통계 주장 금지(등록문대로).
 (c) 정보 조건이 가장 유리함(핵심): H는 p0의 "청크7 call0 읽기 q", 평가는 p4의 "청크7 call0 읽기 q". 같은 청크 번호(같은 RoPE 위치 범위), 같은 denoise step(call0), 같은 층. 다른 것은 prompt뿐이다.
     따라서 이 결과는 "prompt가 달라도 같은 위치·같은 step의 읽기 q 공분산이 전이된다"를 보였을 뿐, 쓰기 시점(call4, context_noise, 청크 c)의 q가 미래 읽기(청크 c+1..c+6, call0–3)에 전이되는지는 전혀 보이지 않았다.
 (d) 비용: quantize_seconds 1.3s(CPU 4스레드, 28080 토큰×12 head)는 RTN의 사전 계산 시간이 빠져 비교 불가(주 작업자 기록 동의). GPU 추정은 §3.
결론 문장: "오프라인(다른 prompt) 읽기-q 공분산을 고정 H로 쓴 code optimization이 같은 바이트에서 단일 읽기 출력 오차를 1/3–2/5 줄인다"까지. 방법 완성 아님, 진단 신호 맞음.

2. causal 후속 검사 — 정보 시점 공정 설계 (반론 포함)
----------------------------------------------------------------------
파이프라인 사실(코드 확인): 청크당 5 call = denoise call0–3 + call4(context_noise 재실행, causal_inference.py:259–268). 캐시에 저장되는 K/V는 call4의 것이다.
 청크 c의 call4 q는 자기 캐시를 읽지 않는다(캐시는 c+1 이후 청크만 읽음). 따라서 "청크 c call4 q로 H_c를 만들어 청크 c K를 양자화"는 쓰기 시점에 실제 존재하는 정보만 쓴다.
 기존 캡처 hook(capture_all_layers.py:38–41)은 count//5=chunk, count%5=call로 이미 call4를 식별할 수 있으므로 새 캡처는 조건만 바꾸면 된다.
세 가지 분포 이동을 분리해야 한다(모두 한 번에 섞으면 실패 원인을 모른다):
 S1 timestep 이동: 쓰기 q(t=context_noise, clean) vs 읽기 q(denoise t, noisy).
 S2 청크/위치 이동: 청크 c의 q vs 청크 c+k의 q (RoPE 위상, 내용 변화).
 S3 prompt 이동: 이미 capacity에서 양성(p0→p4).
팔(결정 팔 3 + 설명 팔 2, 모두 같은 payload):
 A0 RTN(BF16 산술, 기존).
 A1 ONLINE_H: 청크 c(=1..6)마다 H_c = 그 청크 call4 q(회전 좌표)로 OBQ → 청크별 다른 H. 쓰기 시점 정보만. 결정 팔.
 A2 FROZEN_P0_H: capacity와 동일한 p0 청크7 call0 H(오프라인 보정). 결정 팔(선행류 오프라인 보정과 같은 정보 조건).
 A3 FROZEN_P0_WRITER_H(설명): p0의 call4 q(청크 1–6 합산)로 만든 오프라인 H. A2와 비교하면 S1만 분리된다. 선택.
 A4 ORACLE_READER_H(설명, 명시 라벨 "누출 상한"): 평가 읽기 call의 q로 만든 H. 결정에 쓰지 않고 A1/A2가 상한의 몇 %인지만 보고. 주 작업자가 "coincident read q 누출 금지"를 결정 팔에 적용하는 것과 양립한다. 생략해도 됨.
평가(읽기): 새 prompt 청크7 call0(기존과 동일 조건) + call3(마지막 denoise, S1 반대편)의 q 128개(같은 index 규칙). 과거 28080 토큰은 BF16 참조 캐시(call4 K/V) 원본, 현재 청크 BF16.
 참조 = 원본 K·V FP32 CPU attention(capacity와 동일 정의). K-only 참조도 기록.
입력 분리 규칙(필수, 결과 전 고정):
 - H_c 추정에는 청크 c call4 q만. 평가 q(청크7 call0/3)는 A4 외 어느 팔의 코드 선택에도 쓰지 않는다. 코드에서 A1 H 계산 함수가 call==4 텐서만 받도록 assert.
 - 모든 팔이 같은 캡처 텐서(K/V/q/native_av) 해시를 소비하고 결과에 pairwise 해시를 기록(capacity의 source_hashes 방식 재사용).
 - 캡처가 궤적을 바꾸지 않았음: 각 청크 latent가 무훅 BF16 참조와 바이트 일치(기존 byte_equal 방식). 새 prompt는 참조 latent가 없으므로 "훅 없는 run 1회 + 훅 run 1회"의 바이트 일치가 필요 → 생성 2회 상한을 여기에 쓴다. 대안: 같은 run 안에서 native_av와 CPU 재계산 NSE(≤1e-5)로 대체하면 생성 1회로 줄지만 궤적 불변 증명은 약해진다. 주 작업자 선택.
 - 미사용 prompt/seed: 0–9는 K4h8·R-8b·R-8d에 사용, p0/p4는 H 보정·capacity에 사용. 새 prompt는 이 10개 밖이어야 하며 실제 사용 로그(policy_study/reference, kv_headrule_all, kv_alignment_compounding 등록문)의 prompt 문자열 해시와 대조해 결과 파일에 "미사용 확인" 근거를 남긴다. seed도 101/202 밖(예: 303). seed만 바꾸고 prompt를 재사용하면 보류로 인정하지 않는다.
 - A2의 H는 capacity에서 쓴 p0 H와 텐서 해시가 같아야 한다(hessian_raw_sha256 기록 존재).
비용(상한 안인지): 캡처 = 층 18/24 × [청크1–6 call4 q(14MB) + 청크7 call0·call3 각 (q+현재 K/V+native_av ≈ 60MB) + 과거 K/V 1회(200MB) + wo]. 약 2층×(84+120+200)MB ≈ 0.8GB. 무훅 참조 run의 latent 수십 MB. disk 4GiB 안. 생성 2회 = 참조 run + 훅 run. 30분 안(기존 40 forward run이 수 분).
 CPU 평가는 capacity와 같은 규모(청크별 H 6개 → Cholesky 6×12회, 무시). 20분 안.
판정 제안(주 작업자가 결과 전 고정; 수치는 제안):
 신호: A1 이득(전체 참조 sse, A0 대비) ≥ 15% 두 층·두 읽기 call 모두, 그리고 A1 ≥ 0.5×A2(온라인이 오프라인 보정의 절반 이상을 회수).
 종료(온라인 변형): 어느 층/call에서든 A1 ≤ 0%. 이 경우 A2가 15% 이상이면 "오프라인 보정 H 방법"으로만 남는데, 그것은 SAW-INT4/OSCAR류와 정보 조건이 같아 신규성 주장이 더 어렵다.
 판단 불가: 그 사이. 추가 prompt 1개까지만, 이후는 생성 평가로.
 call0과 call3 결과가 반대 부호면 S1이 지배 → A3로 원인 분리 후 재설계(새 후보 아님).

3. 가장 강한 반론 2개
----------------------------------------------------------------------
 R1 (정보): capacity의 양성은 "같은 위치·같은 step" 조건이었다. 쓰기 q(clean, 청크 c)와 읽기 q(noisy, 청크 c+k)는 timestep과 위치가 모두 다르다. RoPE는 상대 위치 회전이므로 쓰기 q의 공분산 고유기저는 읽기 시 상대 오프셋만큼 회전된 기저를 봐야 하는데 H_c는 이를 모른다. 고주파 RoPE 채널에서 H_c가 틀릴 가능성이 크다. Hadamard가 채널을 섞으므로 영향 범위는 예측 불가 → 실측만이 답. 실패 시 "저주파 채널만 H, 고주파는 RTN" 같은 수정은 새 후보로 다시 등록해야 한다.
 R2 (비용): 128단계 순차 루프. GPU에서 head를 배치해도 층당 128 launch×(rank-1 갱신 [4680, 128−j]) = 청크당 3840 launch + Cholesky 360회. launch당 20–50µs면 청크당 0.1–0.2초(추정, 미측정). 청크당 5 forward가 1초 안팎이면 +10–20%로, R-1의 역회전 +8%보다 크다. GPTQ의 lazy-batch(블록 32열) 구현으로 launch를 1/8로 줄일 수 있으나 구현 비용이 든다. "진짜 장애"인지는 CPU 수치로 답할 수 없고, 방법 채택 전 GPU 시간 측정이 필수다. 다만 이 진단 단계의 결정 기준에 넣지는 않는다(정보 시점 질문이 먼저).

4. 지금 가능한 CPU 사전 점검(선택, GPU 0, 수 분)
----------------------------------------------------------------------
 기존 p4 캡처만으로 S3+위치 민감도 대리 측정: p0 H를 "청크7 call0 q 중 앞 1560 토큰(frame 1)만"으로 만들어 뒤 프레임 토큰의 q로 평가하면 같은 청크 안의 위치 이동(RoPE 1–2 프레임)에 대한 H 전이성을 미리 본다. S1은 못 본다. 결과가 capacity 이득의 절반 이하로 떨어지면 R1이 현실적 위험이라는 조기 경고. 이 점검은 결정 기준이 아니며 causal 캡처를 대체하지 않는다.
