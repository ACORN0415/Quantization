== 1. 무엇이 비용인가(형상·산술 기준) ==
- 쓰기 단위: 층당 청크 1개(4680 토큰 × 12 head × 128), 청크마다 30층, 42청크. 읽기(decode) 경로는 B0 Hadamard INT4와 동일하므로 비용 차이는 쓰기에만 있다.
- B0 쓰기: 회전 matmul(4680×128×128 ×12) + 프레임 pad + 그룹 absmax/scale + round/clamp + nibble pack. 모두 병렬, 메모리 바운드(K 29 MB FP32/층).
- OBQ 추가분(codes_obq): head별 128 순차 단계. 단계 j: 열 j 코드 산출, 오차 벡터(4680), 남은 열에 rank-1 갱신 w[:, j+1:] -= err ⊗ u[j, j+1:].
  FLOP 총량 ≈ 4680 × 128²/2 × 12 ≈ 0.46 GFLOP/층·청크 — RTX 4090에서 산술적으로는 밀리초 미만. 실제 비용은 산술이 아니라 "128 × (3~5 커널) 순차 launch"와 글로벌 메모리 왕복이다.
  eager PyTorch 추정: 층당 400~600 launch × ~10 µs ≈ 5~8 ms, 30층 ≈ 150~250 ms/청크 ≈ 청크 시간(1.95 s)의 8~13%. 이것이 "가장 단순한 구현"의 예상 상한이며 측정으로 확정해야 한다.
- 준비 비용(오프라인, 1회/층): H(12×128×128) 역행렬·Cholesky — 무시 가능하나 시간·바이트를 따로 기록. 상주: upper factor FP32 786 KB/층(23.6 MB/30층), 작업공간 4680×128×12×4 = 29 MB/층(일시).

== 2. 비교할 GPU 구현 3단계(새 방법 아님, 모두 GPTQ 공개 구현의 표준 기법) ==
 L0 B0 Hadamard RTN 쓰기(GPU, 같은 파이프라인) — 비용 기준선. OBQ 오버헤드 = L1~L3 − L0로 정의.
 L1 eager batched torch: head 배치(12)·토큰 전체를 한 텐서로, j 루프만 Python. 지금 CPU 코드의 직역. 측정 목적: launch 바운드 상한.
 L2 GPTQ "lazy batch" 블록화(GPTQ 논문 §3의 표준 기법): 열을 블록 B=32로 나눠 블록 안은 순차 rank-1, 블록 끝에 나머지 열을 한 번의 matmul로 갱신(E_blk @ U[blk, rest]).
    launch 수 128→(32×4 + 4) 수준은 같지만 각 단계가 4680×32 슬랩만 만지므로 메모리 왕복이 1/4. 여기에 CUDA Graph 캡처(형상 고정이므로 가능) 또는 torch.compile(mode="reduce-overhead")로 launch 비용 제거.
 L3 융합 커널(아직 미작성): 한 블록이 토큰 행 타일을 맡아 128 feature 보상을 레지스터/공유메모리에서 수행. 기대: K를 한 번 읽고 한 번 쓰는 메모리 바운드(<1 ms/층). 이번 검사에서는 작성하지 않고,
    L2 결과가 아래 문턱을 못 넘을 때만 다음 단계로 등록한다. "직접 커널 0"에 동의.
 이 검사는 L0·L1·L2까지다. L1이 문턱을 넘으면 L2는 생략해도 된다(싼 순서).

== 3. 타이머와 정확성 규정 ==
타이머
- torch.cuda.Event 기반, 각 단계 앞뒤 synchronize. warmup 5회, 반복 20회, 중앙값·p90 보고. 단계 분리: (a) 회전+pad+scale, (b) 코드 선택(OBQ 루프 또는 RTN round), (c) pack, (d) 합계. 준비(H→factor)는 별도 1회 항목.
- 입력은 실제 캡처 K(p4 l18/l24 과거 청크 하나, bf16)로 하고 합성 난수는 쓰지 않는다. 층 2개 측정값 × 30으로 외삽하되 외삽임을 명시(층별 형상이 같으므로 타당).
- 기준 시간: 청크당 생성 1.95 s, forward당 0.39 s(p00 K4h8 sampling.json). 오버헤드 비율은 두 기준 모두로 보고.
- 메모리: torch.cuda.max_memory_allocated 증가분(작업공간 포함), 상주 factor 바이트.
- GPU는 R-8d 완료 후 idle 상태에서, 다른 프로세스 없음 확인(nvidia-smi 기록). 클럭 변동 때문에 L0와 L1/L2를 같은 세션에서 번갈아 측정.
정확성(FP64 CPU ≠ FP32 GPU 가정 금지)
- allow_tf32 = False 고정(matmul·cudnn), 기록. TF32가 켜지면 회전·블록 갱신 matmul이 달라진다.
- 순차 보상은 오차 되먹임이므로 한 코드가 바뀌면 이후 코드가 연쇄적으로 바뀐다. 따라서 "코드 비트 일치"를 합격 조건으로 쓰지 않는다. 대신:
  (i) 코드 불일치 비율(GPU vs CPU FP32 참조, 같은 H·factor·scale)을 보고만 한다.
  (ii) 합격 조건은 출력 지표다: GPU가 만든 코드를 기존 CPU 평가 경로(obq_capacity의 attention·post-Wo SSE, 같은 128 q, 같은 V4)에 넣었을 때
       SSE가 CPU OBQ_FULL SSE의 ±2% 이내(두 층). 이것은 "GPU 구현이 같은 품질의 코드를 만든다"는 뜻이며 비트 동일을 요구하지 않는다.
  (iii) pack/unpack 왕복 정확, payload 바이트가 CPU와 동일(54,097,926 B 기준 분해 재사용).
  (iv) L2 블록화는 수학적으로 L1과 동일 알고리즘이므로 L1 대비 코드 불일치 비율도 보고(FP32 합산 순서 차이만 있어야 함).
- scale은 bf16 absmax/7 → fp16 저장을 CPU와 같은 순서로 GPU에서 계산하고, scale sha가 CPU와 일치해야 한다(scale은 순차 경로가 아니므로 비트 일치 요구 가능).

== 4. 사전 판정(자원 배분용, 품질 문턱 아님) ==
 통과: L1 또는 L2의 30층 합산 OBQ 오버헤드(−L0)가 청크당 ≤ 5%(≈100 ms) 이고 정확성 (ii)(iii) 통과 → 배포 형상 "reader 불변·쓰기 +≤5%"로 기록, causal/rollout 단계의 비용 항목 확정.
 조건부: 5% < 오버헤드 ≤ 20%(≈400 ms) → L3 융합 커널을 별도 등록해야만 비용 주장 가능. 원고에는 "미최적화 구현에서 x%"로만 쓴다.
 실패: L2(블록화+graph)로도 > 20% 또는 정확성 (ii) 실패 → OBQ는 이 배포 형상에서 실용성 미달. 알고리즘 결과는 그대로 두고 비용 결론만 기록.
 상한: GPU 1회 세션 ≤ 15분, 추가 캡처 0, 모델 로드 0(캡처 텐서만), 코드는 새 폴더.
 주의: 비용 측정은 품질과 독립이므로 품질 결과를 보고 비용 문턱을 바꾸지 않는다. 역도 같다.

== 5. 왜 이 기준선인가 ==
- "가장 단순한 강한 GPU 기준선"은 L0(B0 쓰기)이다. 회전 기반 대안(U·UHP)은 L0와 같은 비용이므로 별도 측정 불필요.
- L2는 GPTQ 공개 코드의 표준 블록화라 새 방법이 아니다. L3도 GPTQ 커널 공학이며 논문 기여로 쓰지 않는다(주 작업자 입장과 같음).
- 오버헤드를 forward 시간이 아니라 청크 시간으로 나누는 이유: 쓰기는 청크당 1회(5 forward 중 1회 시점)이기 때문. 두 비율을 모두 적는 것이 정직하다.
