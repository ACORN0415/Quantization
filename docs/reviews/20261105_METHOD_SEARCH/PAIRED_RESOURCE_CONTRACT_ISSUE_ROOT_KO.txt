상태: 실자료 점수/새 GPU 실행0. 사전 제안의 바이트 누락을 교차 검토에서 발견해 정정한다. 팔·rank·cap을 새로 확정한 문서가 아니다.

기존 tensor 계획과 실제 지속 상태의 차이
PSAC rank3의 coefficient+basis+6개 header는1,694,184B다. 그러나 현재 구현은 실제 BF16 복원 후 각 행의 raw query-weighted 오차를 검사하므로, p0의 M[12,128,128] FP64=1,572,864B를 매 쓰기에 사용한다. M도 상주하면 합3,267,048B다. M은 1회 기저 준비가 끝나면 버려도 되는 값이 아니다. CPU 진단에서 다른 팔과 원자료를 공유해 놓았다는 사실도 배포 시 필요한 상태를 없애주지 않는다.
이 full-moment·실제 BF16 row-filter는 공개 QuantWM 정의를 바탕으로 만든 강한 adaptation이다. 원문 D.1은 근사 query-weighted 오차의 개선 여부를 검사한다고만 쓰며 세부 필터 구현을 확정하지 못했다. 따라서 이 구현의 M 비용을 공식 PSAC의 필수 비용이라고 주장해서는 안 된다.

단순 결합을 빠뜨리지 않을 것
FULL+QKSA는 같은 회전·기존 scale을 사용하면 persistent state를 더 만들지 않는 대조 후보다. 실제 읽기 연산과 임시 메모리는 증가하며 OBQ 잔차에서 QKSA 잡음 가정이 맞는지는 별개다.
FULL+PSAC rank1은 FULL U786,432B + PSAC packet/basis1,014,120B =1,800,552B로 기존 제안cap1,806,336B보다 작다. 그러나 full raw M을 더하면3,373,416B다. 따라서 앞 산술만으로 cap내 실행 가능이라고 하지 않는다.

실자료 등록 전에 결정할 사항
1. 모든 팔에서 지속적으로 필요한 통계를 동일하게 세야 한다. payload, GPU 상주 상태, host 상태, 쓰기·읽기 peak를 구분한다. H를 host에 두거나 읽어오는 정책을 허용한다면 저장·전송·계산 비용도 포함하고 다른 팔에도 같은 선택을 허용한다.
2. 논문이 명시하지 않은 row-filter를 full M 검사로 구현한 비용 때문에 PSAC를 단순히 예산 초과로 제외하지 않는다. 원문의 근사 필터를 더 작은 상태로 구현하는 대조 또는 상한 밖의 강한 참조 점을 함께 검토한다. 이를 결과를 본 후 새 팔을 붙이는 근거로 쓰지 않는다.
3. PSAC의 고정 M eigvalsh와 QKSA의 고정 회전 직교성 검사를 청크마다 반복하는 현재 검증 core의 시간을 최적 구현의 필수 비용이라고 하지 않는다. 실제 데이터 효과 측정과 생산용 실행 비용 측정의 범위를 분리한다.
4. 현재 proposal의 같은 cap 내 최선 기준선 gate는 이 미결 사항을 해결한 뒤에만 잠근다. source 준비 완료나 합성 통과를 자원 계약의 완료로 대신하지 않는다.
